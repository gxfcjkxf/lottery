# 品牌钱包与业务关联批量对账交接说明

独立的[品牌业务引用检查](37-brand-business-inventory.md)已接入，从声明的41张品牌来源表出发发现账户或父记录缺失，不依赖本模块捕获的钱包范围。它是单次结构观察，不回写本模块旧任务或替代金额链核对；两种结果应分别解释。

后台可提交当前品牌全部钱包的持久检查任务，选择仅钱包或钱包与业务关联检查，查看每个账户的余额、账本及资金业务引用差异，并在技术失败后人工恢复未完成目标。任务只检查，不调整积分、不自动修复余额，也不产生充值、提现、派奖或奖金冲正。已存在的单会员修复流程仍需重新获取实时预览并单独确认。

## 范围与权限

创建时固定该品牌现有账户和成员的范围，最多100000个账户。后续注册账户不追加到旧任务；未完成目标按实际检查时的数据记录结果，不把分批观察冒充全品牌同一时点余额快照。一个品牌同时只允许一个pending或running任务；其他品牌独立处理。

查看使用`wallet.view.brand`并具备当前品牌范围，或独立的`wallet.view.platform`授权；平台查看不要求伪造品牌成员，超级管理员标记本身不授权。创建和重试还必须具备当前品牌范围的`wallet.reconcile.brand`，超级管理员只读。品牌暂停可检查，停用品牌只允许读取；已经接受的任务继续完成。迁移为已有品牌引导角色增加新权限，新引导管理员也包含该权限，普通角色仍需明确配置。

所有查询、授权和任务写入使用主库，不进入历史从库白名单。查询审计提交后才返回数据；权限撤销、会话失效和审计故障不能利用旧回执或从库绕过。

## 已实现接口

共同前缀为`/api/v1/admin`，每个接口要求`X-Brand-ID`。JSON和认证通用约束见[接口合同](04-api-contract.md)，可调用模型以[OpenAPI](openapi.json)为准。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | /reconciliations | 当前品牌任务列表 |
| POST | /reconciliations | 捕获账户范围并创建任务，201 |
| GET | /reconciliations/{id} | 当前任务状态及计数 |
| GET | /reconciliations/{id}/targets | 目标及历史观察结果 |
| POST | /reconciliations/{id}/retry | 人工恢复失败目标，200 |

创建正文为`{reason,check_scope?}`；省略check_scope表示旧版`wallet`，也可显式选择`wallet`或`wallet_and_business`。显式null、重复键、未知字段和未知范围拒绝。重试正文恰好为`{version,reason}`，版本须小于9007199254740991，以便生成下一版本。原因须已去除首尾空白，非空，最多500个UTF8字节，不含NUL、CR、LF。两个POST需要幂等键，Cookie还需可信Origin。GET不接受正文，包括null；列表和目标支持规范十进制`limit`1至100、默认20，以及`offset`0至1000000；目标可按`outcome=pending|failed|consistent|repairable|corrupt`筛选。未知、重复、空查询参数、裸问号及带正号或前导零的分页数拒绝。

创建回执固定为首次pending/v1、原目标数及原检查范围；即使worker已完成任务，原键重放仍返回该原始回执。旧reason-only请求的摘要算法不变；同键改为业务关联范围返回冲突，不能升级旧回执。重试回执为pending、原业务版本加一，保留已检查目标、原开始时间及检查范围。GET提供当前状态，不能代替未知写入的原回执确认。品牌停用、撤权或退出后重放也重新执行授权检查；审计等待结束后还要复核会话，过期时新任务、审计和回执一并回滚。活动任务冲突返回409，超过账户范围上限返回413，不提交半个任务或孤立审计。

主要错误为`RECONCILIATION_INPUT_INVALID`、`RECONCILIATION_NOT_FOUND`、`RECONCILIATION_STATE_CONFLICT`、`RECONCILIATION_VERSION_CONFLICT`、`RECONCILIATION_TOO_LARGE`，以及通用会话、权限和存储错误。版本最大9007199254740991；任务计数和积分均为规范十进制字符串，客户端不得把积分转为Number。

## 任务与观察结果

Job包含编号、品牌、状态、版本、check_scope、范围/已检查/一致/可修复/异常/失败/待处理计数、创建人员与原因、创建/首次开始/完成时间、最近错误、可重试标志和创建审计编号。范围计数等于已检查、失败和待处理之和；已检查数等于三种观察结果之和。`can_retry`表示任务处于技术失败状态，仍需当前权限、版本、品牌状态及没有其他活动任务才可执行重试。

状态为pending、running、completed或failed。检查出余额差异或账本损坏也是一次已完成的观察，不属于技术执行失败；全部目标检查完毕后任务completed，但这不表示所有账户都一致。空范围任务由worker完成，不能将没有账户解释为有资金结论。

Target保存编号、品牌、任务、账户、成员、check_scope、pending/checked/failed状态、尝试次数、错误码、观察时间和审计编号。checked目标才有outcome和preview；只有业务关联范围的checked目标有business_preview，其他当前响应均为null。历史旧回执可缺少新增字段，客户端只按wallet解释，不把它当成新的完整检查。技术失败仅返回`CHECK_FAILED`，不暴露连接串、SQL异常或内部堆栈。

preview沿用单会员修复预览：账户/成员、实际账户版本、完整账本版本计数、实际存在的分项、账本重建期望余额、consistent/repairable、问题列表和绑定观察内容的token。实际分项稀疏保存，缺失桶不补零；期望分项包含四来源乘四状态的完整整数矩阵。未产生账本的账户版本可以为0。

- consistent：完整账本版本链、摘要、前后快照、来源分配、冲正引用及实际16桶均一致；旧完整12桶仅在读取时以佣金零值规范化。
- repairable：账本完整性可证明，但余额桶或账户版本投影存在差异；任务不执行修复。
- corrupt：账本完整性不能证明，或在业务关联范围内存在关联问题；不允许根据该结果重建余额或自填金额“补平”。钱包preview与业务preview分别保留真实判断，业务异常不能被钱包一致或可修复覆盖。

观察是历史证据。后续充值、投注、派奖、退款或人工修复不会改变旧结果；处理差异时前往「资金与账本」中的「余额差错处理」，重新获取实时预览。旧token不能授权随后改变的账户。

## 业务关联范围

0061与0062提供只读业务引用，0063将它们与当前被检查账户的实际流水双向核对。支持的业务和手工资金种类如下；按固定family排序返回覆盖计数，即使某种业务为零也保留该项。

| family | 核对对象 |
|---|---|
| bet | 原注单扣款、来源分配和投注审计 |
| commission | 原已派发非零目标与佣金来源入账 |
| commission_adjustment | 独立人工差额修正及前后金额、操作审计 |
| commission_correction | 真实已执行非零更正、批准证据及apply步骤 |
| manual | adjust、adjustment、freeze、unfreeze、withdrawal_transfer、reversal及精确积分审计 |
| prize | 历史paid目标的非零中奖计算和实际派奖，包括已被新代次取代的记录 |
| prize_reversal | 原历史派奖与实际开奖结果更正反向记录 |
| recharge | confirmed人工充值及确认人员、金额和审计 |
| refund | 取消注单全额原分配退款及期次取消目标 |
| reward | 原奖励发放和已撤销的完整反向记录、独立动作历史 |
| unknown | 不在当前实现清单内的流水类型，明确报不支持而不猜测业务 |
| withdrawal | 四来源申请预留、实际内部出款或原路释放及状态动作 |

核对绑定品牌、账户、会员、类型、业务编号、操作键、来源分配、变动金额、冲正引用及相应操作审计。所有流水要求恰好一条匹配的points审计，包含实际流水编号、账户版本及精确前后余额。历史业务引用以实际已发生的资金记录为依据，不要求它仍是当前计算代次。零额佣金目标和真实零奖无需伪造流水；应入账但缺少保存指针、动作或计算的记录不得因内连接而被忽略。

business_preview是封闭对象，字段为account_id、member_id、account_version、ledger_entry_count、business_reference_count、issue_count、issues_truncated、consistent、fingerprint、issues、coverage。版本与钱包preview一致；流水数量与其ledger_version相等。三个总数及各family计数为无损非负十进制字符串，客户端以BigInt核对合计。coverage恰好为表中十二项；issues最多100项，issue_count包含全部问题，超过100时issues_truncated为true。consistent只在issue_count为0时成立。

每个issue仅包含code、可空entry_type、可空ledger_entry_id、resource_type、可空resource_id。code为UNSUPPORTED_LEDGER_TYPE、MISSING_BUSINESS_RECORD、INVALID_BUSINESS_BINDING、MISSING_LEDGER_ENTRY、DUPLICATE_BUSINESS_BINDING或INVALID_MANUAL_AUDIT；entry_type遵守现有1至200位ASCII字母、数字、下划线、点、冒号和连字符的流水标签规则。一个损坏绑定可能产生多项诊断，不能把问题数当成异常订单数。

fingerprint为绑定账户和完整检查材料的SHA-256诊断摘要，不返回私有规则、支付证明、身份资料或内部原因，也不是修复授权。结果写入时数据库在同一账户共享锁内独立重新计算业务preview，拒绝伪造的“全部一致”结果；仅让伪造结果与伪造审计一致仍不能通过。钱包链和修复token的既有算法保持不变。

## 数据与事务边界

0038新增`point_reconciliation_jobs`、`targets`、`results`、`failures`和`retries`五表，不改旧资金或账本。任务创建、目标捕获、创建审计和幂等回执同事务；范围来自一个账户查询快照，随后按已捕获ID持久化，不以第二次全表查询混入新账户。

任务保留64位`creation_xid`，目标只能在该创建事务内插入；不能在提交后、即使任务仍pending/v1时追加目标。使用顶层事务编号兼容变更引擎的savepoint，不将子事务行xmin误当成顶层编号。该函数的顶层事务行为见[PostgreSQL事务编号说明](https://www.postgresql.org/docs/17/functions-info.html#FUNCTIONS-TXID-SNAPSHOT)。这个字段是内部边界，不对客户端开放。

结果、失败尝试和人工重试证据不可更新或删除，结果必须与账户观察和同事务审计匹配。checked目标不能重新打开；completed任务不可改写或删除。延迟约束核验创建范围和完成状态，未检查目标不能伪装为完成。中间步骤不每次重扫全体目标；最终完成时核对完整范围，目标分页只为当页生成预览JSON，计数和页使用同一语句快照。

原账户、16桶余额、经济账本、修复记录和outbox不由检查任务修改。已发现损坏时现有记账完整性检查继续拒绝不安全写入；此任务本身不新增封禁、冻结或自动资金补偿策略。

0061至0063不回填旧检查的业务结论，也不重算旧结果、审计或幂等回执。旧任务check_scope默认wallet，旧结果business_preview为null。迁移必须先于新API和worker启动；新前端接受旧缺字段的wallet回执，同时拒绝全范围checked响应缺业务preview或混用范围。

## Worker与故障处理

worker有独立一秒循环，每轮最多20个提交步骤，硬上限100；不阻塞期次时钟或开奖循环。多进程用任务锁及SKIP LOCKED协调，目标只产生一份结果。每步只持有一个账户共享锁，正常记账使用排他锁；热账户被延迟一秒而不等待占住整批。任务按最近处理时刻轮转，避免单个大品牌持续压住其他品牌。

完整账本检查的子上下文限两秒。已知目标的技术错误先回滚本次数据，再以独立短事务保存失败尝试、失败审计和任务failed状态；该状态不自动重试。人工重试带理由和当前版本，只恢复失败目标，保留先前成功检查、失败历史和首次开始时间。程序退出或数据库/审计故障导致失败证据也无法提交时，未提交目标保持pending，恢复后的worker可继续；不能声称未落库的失败已经暂停任务。

提交确认丢失后，通过新的主库事务重查目标状态；已有checked证据不能被后续失败记录覆盖。后台只显示固定错误码，运维需结合受控进程日志、数据库状态和审计定位基础设施故障，不把敏感SQL异常写入客户端。

## 后台与验收

PC和移动端入口为「批量对账」。创建可选择「仅钱包」或「钱包 + 业务关联」，确认页、原回执及当前详情分别显示范围。创建、重试先冻结正文与键，再由单人核对确认；存在未知请求时范围选择禁用。丢失、畸形成功回执或服务错误保留未知请求；只读刷新和切换页面不能确认它，返回后可显式按原请求重放。退出或切换账号清除旧意图，迟到响应不能改写新会话页面；完整浏览器刷新丢失内存意图不在本次自动恢复范围内。

筛选变化立即清除旧结果，不把原筛选内容放在新筛选标题下。客户端校验品牌、任务、计数、时间、来源矩阵及观察状态，不能把缺失余额桶、互相矛盾的“正常”标志或无完成时间的响应显示为通过。错误提示在内容区域内显示，不挡住移动导航。

真实数据库回归涵盖捕获范围、三类结果、资金指纹不变、禁止伪完成和晚插入目标、热账户与另一品牌、多worker去重、技术超时、审计故障及人工恢复后旧观察不变。HTTP回归涵盖检查后原始创建/重试回执、同键异体、活动任务并发、品牌权限、审计回滚及严格参数。浏览器在专用库执行真实201后丢回执、离开/返回原键确认、实际worker完成、筛选三类观察及无修复请求，覆盖1440px与360px。

本功能核对捕获账户内已实现资金业务与经济账本的关联，不证明全品牌同一时点快照、独立于账户范围的全部业务表无孤立行、真实外部支付到账、不可变日月结或生产账务验收。100000账户只是资源上限，不是已验证吞吐或完成时限；长账本、大范围任务与500次/秒投注并行仍需专项压测。原开发库不注入测试差错；最终交付仍需客户人工代码审核。

固定字段证据见[钱包对账验收报告](performance/s7n-wallet-reconciliation.json)。CI使用独立数据库`lottery_reconciliation_browser`，夹具命令只在`browserfixture`标签下编译，要求test环境、明确确认、指定回环地址/端口/用户及空钱包库；拒绝连接重定向和原开发库。它先产生三条真实测试赠送，再只在专用库注入余额差异和账本损坏，损坏注入事务恢复不可变触发器后才提交。该操作只用于功能测试，普通生产构建和开发库不执行。
