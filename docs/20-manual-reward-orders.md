# 人工奖励订单与全额撤销

0055接入品牌后台人工奖励订单、实际赠送积分入账、全额撤销及余额不足的人工待处理。第一期不实现代理、推荐或活动自动奖励，也不接入外部资金。管理员提交发放请求就是单人批准，独立权限和审计不能由通用积分调整代替。后台“人工奖励”已接入真实接口、双语响应式页面和同会话请求恢复；0056追加三种历史站内通知，0057追加两种独立报表及工作台状态计数，见[奖励报表合同](21-reward-reports.md)。客户人工审核及生产验收仍须完成。

## 状态与资金动作

| 当前状态 | 操作与条件 | 新状态 | 资金动作 |
| --- | --- | --- | --- |
| 无订单 | 有权管理员明确发放 | granted 版本1 | 正额增加gift.available |
| granted | 明确撤销且赠送可用足够 | revoked 版本加1 | 全额反向原奖励入账 |
| granted | 明确撤销但赠送可用不足 | revocation_pending 版本加1 | 无积分变动 |
| revocation_pending | 人工继续且赠送可用足够 | revoked 版本加1 | 全额反向原奖励入账 |
| revocation_pending | 人工继续但赠送可用仍不足 | revocation_pending 版本加1 | 无积分变动，记录本次尝试 |
| revoked | 任意撤销或继续请求 | 拒绝 | 不重复扣款 |

只使用原品牌、原会员的gift.available。冻结积分、提现占用积分和其他来源不能用于撤销；没有自动解冻、部分追回、负余额或欠款。后来补充赠送可用积分不会自动恢复，需要运营重新核对真实版本、填写原因并明确继续。待处理并不另冻结其他积分，也不回退既有投注、取消或提现业务。

不足是持久化的业务结果，HTTP返回200及revocation_pending，不返回可被客户端自动重试的余额错误。技术、审计或账本失败则整笔回滚，不能留下只有订单或只有积分的成功记录。

## 账本与并发

发放entry_type为reward_grant，reference_type为reward_order，reference_id为订单编号，operation_key为`reward-grant:<订单编号>`。撤销为reward_reversal，同一订单引用、`reward-revoke:<订单编号>`及reversal_of原发放账本。两者只改变赠送可用桶，记录全部16桶之前、变动及之后积分。原积分值、原发放订单、原因及账本始终保留，不覆写或删除。

积分使用正int64字符串，版本是1至9007199254740991的安全整数；不能在最大版本继续递增。实际增加仍受当前积分余额上限和int64约束，撤销不因后来降低余额上限而受阻。奖励不是通用钱包调整，不借用调整限额或权限作为发放授权。

写入先取得品牌共享准入锁，再取得订单及钱包锁；钱包和交叉锁使用NOWAIT，忙返回不缓存的503。按账户锁串行核对账本尾与当前完整余额，损坏时停止，不补写余额。并发撤销只有一个原奖励反向流水，其他请求收到版本、状态或锁忙冲突。

数据库保存reward_orders当前状态及原grant身份，reward_order_actions保存每次grant/revoke/retry的版本、前后状态、操作人、原因、审计与实际ledger关联。订单身份和原额不可修改，动作和审计不可删除；不足动作没有ledger。匹配的人工审计、真实不足、精确赠送来源和金额、原流水引用及完成状态均受守卫检查。延迟提交约束拒绝孤立订单、动作或账本；通用points.Reverse不能绕过奖励撤销。

## 管理接口与权限

所有路径位于`/api/v1/admin/reward-orders`。查询要求reward.view品牌或平台；写操作另要求对应的品牌动作权限。超级管理员只读，其他资源的wallet、recharge或commission权限不授权奖励操作。品牌paused可以处理财务，disabled拒绝新发放、撤销及人工继续，但保留有权限的查询。

| 方法与路径 | 权限 | 正文与成功结果 |
| --- | --- | --- |
| GET集合 | reward.view | limit/offset，200订单分页 |
| POST集合 | view加reward.grant.brand | member_id、points、reason；201原发放回执 |
| GET /{id} | reward.view | 无查询参数，200当前状态 |
| GET /{id}/actions | reward.view | limit/offset，200不可变动作历史 |
| POST /{id}/revoke | view加reward.revoke.brand | version、reason；200原撤销回执 |
| POST /{id}/retry-revocation | view加reward.retry.brand | version、reason；200原人工继续回执 |

分页默认20、上限100、offset上限1000000。未知、重复、空或非规范数字参数以及任何GET正文拒绝；详情不接受查询参数。跨品牌会员和订单不返回其他品牌数据；无对应品牌权限先拒绝，不通过404暴露目标是否存在。读取使用主库repeatable-read及当前授权，查询审计成功提交后才释放数据，审计等待期间会话过期则回滚。

三种写操作必须带Idempotency-Key与确认时冻结的X-Reward-Actor-ID。该UUID不是权限凭据；服务在首次执行和回执重放前重新认证、核验当前权限、品牌状态及actor一致性。正文严格闭合，字段不可缺省、重复或null；原因不规范空白、不接受Unicode控制字符且最多500 UTF-8字节。写接口不接受查询、账户编号、外部支付、指定ledger或系统身份。

原始正文、品牌和目标参与幂等摘要。同键同请求返回原版本与原状态，不由后来撤销或重试后的状态覆盖；同键异意图返回409。网络未知时客户端必须使用原普通JSON快照、actor、品牌、目标、正文及键恢复，不先读取新版本后改写旧请求。写方法不隐式重新查询或切换账号；当前状态另用GET读取。

## 公开数据与升级

订单DTO保留编号、品牌/会员、正整数积分、状态/版本、原发放与撤销ledger编号、创建及最后审计、操作者、原原因、积分政策版本和时间。所有空撤销字段显式null，不暴露账户编号、原始余额、钱包桶或私有账本快照。动作分页显式带brand_id和order_id，即使空页也可核对目标；动作按版本降序，订单按创建时间及UUID降序。

客户端严格校验闭合DTO、品牌/目标、版本与状态空值关系，积分与计数保持精确字符串，日期比较保留微秒/纳秒，不用毫秒截断误判排序。当前查询不是余额证明，历史动作也不表示今天仍有同额积分。

0055只新增奖励表、守卫、索引及独立权限；不给旧赠送积分补造奖励订单，不改既有钱包、账本、佣金、身份或审计。已有自定义角色不会自动获权，服务器引导品牌角色追加奖励操作权限，平台引导角色只追加查看。原迁移文件不修改；升级前后资金证据与重复迁移须验收。

## 剩余验收

独立业务报表和工作台状态计数已接入；两种报表不能作为封存日月结或当前可用余额证明。真实设备、完整容量、生产部署与客户人工代码审核另行验收。

## 后台操作与请求恢复

进入“人工奖励”后，选中真实品牌读取20条分页订单，详情与20条动作历史独立刷新。发放填写会员UUID、正整数积分和原因；撤销或继续须使用当前详情版本。先核对冻结的普通JSON、操作人、品牌、目标、原正文与幂等键，再明确勾选确认；页面不代替服务端权限、幂等或账本校验。新建服务器引导账号同样获得显式奖励权限，平台引导账号仅奖励查看。

网络、5xx或畸形回执留下同会话内存请求，禁止另建资金意图；列表、详情或历史后来读到新状态不代表旧请求已确认。离开再返回仍需核对原意图，使用原actor、正文、版本和键重试，不能替换成新版本。原回执与当前查询分开展示，例如重放发放回执仍为granted版本1，而当前详情可能已经revoked版本2。

确定409也保留旧意图，必须成功刷新相关读取、人工核对并明确确认丢弃，之后才能新建请求。迟到409在离开页面后仍标记冲突，不静默解锁。有效回执一旦确认就移除原待确认意图，立即使旧详情版本不可操作；后续GET失败不将已确认写入变为未知，也不自动重发。注销、401和账号变化清理内存；失去权限、切换品牌及迟到响应不能把请求改绑到另一账号或品牌。请求不写入localStorage、Cookie或其他持久存储；完整刷新后不自动恢复或提交资金请求，需运营查询实际订单和审计再处理。

中英文切换只更新文案，不重读、不改原因或积分、不发送奖励请求。disabled品牌只读，paused仍按独立权限处理；超级管理员不能发放、撤销或继续。

## 独立浏览器测试环境

`scripts/prepare-reward-browser.mjs`仅允许明确确认的test环境、loopback数据库与精确desktop/mobile数据库名。它先核对空public表和实际数据库身份，再依次执行正式migrate、seed和两个create-admin；运营账号绑定Aurora，平台账号只读。已有表即拒绝，不重置、不放宽权限或账本守卫，不启动worker。继承的PostgreSQL覆盖环境移除，凭证只传入对应账号引导进程，错误不输出子进程原文或密钥。

`tests/browser/rewards.spec.ts`使用正常后台API新增会员，实际UI发放与撤销、正式冻结/解冻和显式人工调整准备其他来源。丢失回执在真实提交后发生，不伪造余额或成功响应；重放使用同actor、正文和键，核对原回执与当前状态、16桶前后值、唯一原奖励反向账本、待处理无资金移动及只读账号不写入。CI为两个视口使用不同空库，专项重试为0，零测试或任何跳过都失败；这不替代苹果、安卓、鸿蒙真机验收。

## 历史站内通知

0056为每个新提交的动作追加granted、revocation_pending或revoked事件，同事务匹配真实不可变动作、审计和完整赠送账本。待处理没有账本或积分移动，重复原请求不追加事件；运营显式继续仍不足是另一个动作历史。事件以动作UUID区分，用户只取得原订单UUID及原奖励正额，不取得操作原因或账本见证。后来已撤销仍可投递先前待处理消息，且有不可编辑的说明强调“本次没有积分变动”，不是今天的状态或余额。

三种消息包括v1均须保存双语模板快照。发布或修改模板不改旧消息，消费者不改钱包；既有站内信的已读幂等流程继续适用。0056保留原defaults函数OID、旧十六类配置/修订及全部财务事实，只追加三类初始模板。旧奖励不回填事件，旧待处理订单升级后经明确继续，仅为新动作生成消息。私有事件见证、公开字段及消费守卫见[通知合同](12-notification-templates.md)。

奖励CI在手工资金流程完成后，另启动既有平台worker验证真实站内信；它不是新奖励发放worker，也不打开佣金派发或接入支付。专项用户页面验证三种消息、编辑模板后原快照保持、不可编辑的双语历史说明、已读丢失回执的原键重放及钱包/账本不变。两个视口各有独立测试库，初始化脚本自身仍不启动worker。
