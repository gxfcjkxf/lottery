# 人工奖励发放与全额撤销

2026-10-27 一期精简为两个状态：`granted`（已发放）和 `revoked`（已撤销）。管理员明确发放即单人批准；不提供待追缴状态、继续撤销接口、自动追缴或欠款。

## 资金动作

发放在同一事务创建订单、不可变动作、赠送可用积分入账、审计和历史通知。撤销只能全额反向原奖励的 gift.available 入账；余额不足返回 **422 REWARD_AVAILABLE_INSUFFICIENT**，订单状态和版本、动作、钱包、资金流水及通知均不变。冻结、提现占用及其他来源不参与扣款。运营确需再次撤销时，在余额恢复后提交新的普通撤销请求。

发放流水为 reward_grant，键为 `reward-grant:<订单编号>`；撤销流水为 reward_reversal，键为 `reward-revoke:<订单编号>`，reversal_of 绑定原发放流水。两者引用 reward_order，保留完整16分项快照。禁止负余额、部分追回、修改原流水或通用冲正绕过奖励撤销。

保留品牌和会员隔离、独立权限、当前操作者认证、订单版本、钱包锁、资金幂等及数据库订单／动作／流水的原子性约束；重复撤销不得重复扣款。

## 接口

品牌后台前缀为 `/api/v1/admin/reward-orders`，所有接口要求明确品牌。总后台只提供相应查询。

| 方法 | 路径 | 结果 |
| --- | --- | --- |
| GET | 集合 | 订单分页 |
| POST | 集合 | 201 原发放回执 |
| GET | /{id} | 当前订单 |
| GET | /{id}/actions | 不可变动作历史 |
| POST | /{id}/revoke | 200 原撤销回执；积分不足为422 |

查看使用 reward.view，发放和撤销分别要求 reward.grant.brand 和 reward.revoke.brand；平台管理员只读。写请求保留 Idempotency-Key 和冻结的 X-Reward-Actor-ID，并在首次执行和回执重放前重新授权。品牌暂停可处理财务，停用后只读。

## 后台与通知

页面只展示发放、撤销及相应历史，不再展示“待处理”“继续撤销”按钮或相关报表计数。仅成功发放和撤销产生历史通知；积分不足不通知会员。

网络结果未知时仍保留原操作者、品牌、目标、正文和幂等键，按原请求确认，不能创建重复资金意图。明确422结束本次请求；修正条件后可提交新请求。历史回执与当前订单分开读取。

该版本直接收敛当前基线，不兼容旧待处理状态或旧继续撤销接口。
