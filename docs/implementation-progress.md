## 验收原则

- S1 的原型数据须明确标记模拟；任何原型成功提示不得宣称账本业务已执行。
- PostgreSQL 是业务事实来源；不能用内存余额替代资金实现。
- 阶段完成须记录执行命令与实际结果；500 次/秒目标必须由真实业务压测证明。
- 本任务授权开发与阶段提交，不授权部署到客户生产环境。
- 文档默认技术参数可以由实施者确定并记入决策记录；涉及派奖、佣金分配、提款流水公式等业务选择须保留未决标记。

## 测试策略

- 核心业务采用 TDD，先覆盖不变量、错误和并发路径，再实现正常流程；UI 采用可交互原型与浏览器回归迭代。
- 后端使用 Go 测试与真实 PostgreSQL；前端使用 Vitest、类型检查和 Playwright（1440px PC / 360px 移动视口）。
- CI 将后端 race 检查、前端检查与带独立数据库的浏览器测试分成三个任务。测试环境不开真实支付。
- 本机缺少 Docker 和 C 编译器：数据库集成测试已用隔离的本地 PostgreSQL 执行；Compose 和 race 的实际验证需由具备运行条件的环境执行，不能声称本地已通过。

## 文档勘误

- 全局身份属于平台；品牌用户操作权限与全局密码的影响范围需分别校验。
- 规则审核继续遵守创建者不得自审，通用单人流程不会解除玩法审核要求。
- 余额 API 统一以十进制字符串返回 64 位整数，前端使用 BigInt；避免 JavaScript 安全整数溢出。
- 冻结与提现必须保留每种来源的状态分配；只记录三种可用来源余额不足以实现完整原路退款。
- 相同投注内容允许用户有意重复购买；幂等依据客户端操作键和请求摘要，不以内容相同误杀合法订单。

## S3-a 积分账本与人工财务（2026-10-06）

前置 S2-b 已提交并推送 main：`32c8e64326d8d742f74e840c2587a226ba701777`。

本子阶段交付：

- 真实 PostgreSQL 事务账本：充值/中奖/赠送三个来源 × 可用/人工冻结/系统冻结/提现四个状态，合计 12 个独立分项。API 积分统一为有符号 64 位整数的十进制字符串，前端按 BigInt 运算；积分不过期。
- 每笔流水保存全部分项的 before/delta/after、来源分配、账户递增版本、业务引用、幂等摘要与操作人信息；同事务更新余额、写不可改写流水和审计。显示积分含可用与冻结，不含提现积分；来源汇总字段是各来源的可用积分，不再重复相加。
- 人工创建待确认充值单，确认后才入账；单人操作、原因必填，可选文本凭证引用和备注。没有支付接口、真实出款或文件上传。
- 人工冻结按充值→中奖→赠送分配；解冻必须引用原冻结流水，整笔原路返回且只能成功一次。按来源人工增减可用积分，不能任意修改状态或绕过非负限制。
- 同账户排他锁、分配前锁定、幂等重放与请求冲突保护；余额与最近流水不一致、缺失分项、整型/版本溢出时停止写入，不自动捏造历史或修正余额。冲正追加新流水，不能修改旧流水。
- 用户端钱包、来源/状态明细、流水分页；管理端余额、充值创建/确认、冻结/解冻、来源调整、逐笔对账均接入真实 API，支持 PC 与移动视口。后台页面按精确权限显示；品牌隔离与写入权限服务端重查。
