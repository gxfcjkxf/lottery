## 验收原则

- S1 的原型数据须明确标记模拟；任何原型成功提示不得宣称账本业务已执行。
- PostgreSQL 是业务事实来源；不能用内存余额替代资金实现。
- 阶段完成须记录执行命令与实际结果；500 次/秒目标必须由真实业务压测证明。
- 本任务授权开发与阶段提交，不授权部署到客户生产环境。
- 文档默认技术参数可以由实施者确定并记入决策记录；涉及派奖、佣金分配、提款流水公式等业务选择须保留未决标记。

## 测试策略

- 核心业务采用 TDD，先覆盖不变量、错误和并发路径，再实现正常流程；UI 采用可交互原型与浏览器回归迭代。
- 后端使用 Go 测试与真实 PostgreSQL；前端使用 Vitest、类型检查和 Playwright（1440px PC / 360px 移动视口）。
- CI 将后端 race 检查、前端检查与带独立数据库的浏览器测试分成三个任务。测试环境不开真实支付。
- 本机缺少 Docker 和 C 编译器：数据库集成测试已用隔离的本地 PostgreSQL 执行；Compose 和 race 的实际验证需由具备运行条件的环境执行，不能声称本地已通过。

## 文档勘误

- 全局身份属于平台；品牌用户操作权限与全局密码的影响范围需分别校验。
- 规则审核继续遵守创建者不得自审，通用单人流程不会解除玩法审核要求。
- 余额 API 统一以十进制字符串返回 64 位整数，前端使用 BigInt；避免 JavaScript 安全整数溢出。
- 冻结与提现必须保留每种来源的状态分配；只记录三种可用来源余额不足以实现完整原路退款。
- 相同投注内容允许用户有意重复购买；幂等依据客户端操作键和请求摘要，不以内容相同误杀合法订单。

## S2-a 账号与品牌成员链路（2026-10-06）

本次是 S2 的子阶段，不表示完整 RBAC 管理或整个订单已经完成。

已实现并接入真实 PostgreSQL：

- 用户名/手机号注册与登录、全局凭证、品牌首次加入与条款同意、品牌成员资料、缺失身份字段仅补填一次。
- 用户/管理账号独立会话；品牌 Cookie 隔离、HttpOnly/Strict、数据库仅存令牌摘要，退出/踢人/禁用会话即时检查。
- 注册同时创建零积分账户及来源/状态桶，仅初始化账户，不提供充值、投注或派奖。
- 管理账号 CLI 显式引导，无默认密码；多角色权限并集去重、品牌范围授权；超级管理员只查看用户，不改状态、不重置密码、不踢人。
- 管理端真实品牌选择、成员列表、状态/备注变更、踢人、全局密码重置、审计查询；用户端真实注册、登录、资料和退出。其余资金/审核/配置页面仍明确标记演示。
- PostgreSQL 持久化幂等、请求 HMAC、AES-GCM 响应加密并绑定请求作用域，重复写不重复产生会话/审计，失败业务回滚。
- 认证跨实例限流、基础图形验证码及一次性挑战；代理 IP 仅信任显式网段，禁止通过伪造转发头绕过。
- 提交前安全复查发现并用失败回归复现两个问题：固定 Telegram/验证码标识共用账号额度，以及品牌局部权限修改跨品牌共享密码。已改为未验证请求只按 IP 限流、验证后的 Telegram ID 各自限流；密码重置先检查全部已加入品牌的权限（此业务保护规则待用户确认）。
- Telegram OIDC 签名、签发方/受众/时间/nonce 校验、固定 JWKS 地址与缓存、全局身份/绑定限制；前端官方授权入口和超时恢复。默认关闭，真实外部授权尚未验证。
- 成功管理查询、用户/管理登录与人工操作审计记录，含 IP、请求 ID、前后状态；密码与令牌不进入明文日志。
- 新增不可变迁移 `0003`、`0004`；本地和 CI 使用独立测试凭证，不接入客户保密材料。

## 未决业务选择

- 跨品牌共享密码重置：当前安全默认要求操作者覆盖该用户所有已加入品牌的重置权限；已询问用户确认，另一选项是仅用户自行重置共享密码。未确认前不放宽。
- 结算：计算后自动派奖，还是由运营确认；用户短回复“1”的指向仍待确认。
- 多层代理佣金采用差额分配还是各层独立计算。
- 开奖纠正时旧中奖积分不足冲正的处理（人工阻断/补足或负债规则）。

这些未决选择不阻塞基础工程，但相应业务模块不得按未经确认的选择上线。
