## 0. 产品框架讨论

本节用于确定产品边界和系统分层。已确认内容记录在 0.1 和 0.2，仍需决定的事项保留在 0.3。

### 0.1 业务形态

已确认：

- 系统按多租户平台设计，支持多个品牌。
- 每个品牌具有独立的用户、余额、订单、游戏配置和后台管理员。
- 品牌之间的数据、资金账本、订单和后台权限必须隔离。
- 第一阶段先提供彩票游戏模块。
- 总体架构按可扩展的完整运营平台设计，为后续增加其他游戏或业务模块保留扩展能力。
- 第一期开奖采用外部开奖结果源，并支持人工补录；平台自开奖保留为后续扩展能力。

### 0.2 系统分层

按以下层次规划系统：

1. **品牌与租户层**：品牌、租户、域名、主题、功能开关和数据隔离。
2. **用户端**：注册登录、游戏大厅、选号或参与、订单、开奖结果、账户和帮助中心。
3. **运营后台**：用户、游戏、期次、订单、开奖、派奖、公告、客服和运营配置。
4. **平台核心服务**：用户账户、游戏规则、期次状态、订单状态、中奖判断、结算和通知。
5. **资金账本层**：账户余额、充值、提现、奖金、退款、冻结、人工调整和对账记录。
6. **支付接口层**：支付机构和钱包接口；第一阶段保留接口边界，暂不接入真实支付服务。
7. **开奖来源层**：第一期使用外部开奖结果和人工补录；架构预留平台自开奖能力，按游戏类型配置可用来源。
8. **合规与风控层**：身份验证、地区限制、年龄限制、限额、异常行为、冻结、审计和责任博彩。
9. **外部接口层**：支付机构、身份验证服务、开奖结果源、消息服务和客户已有系统。
10. **数据与审计层**：业务数据库、操作日志、开奖记录、订单快照、资金流水、报表和不可篡改要求。

## 4. 待确认的核心问题

### 4.1 玩法

- 首期重点支持三类主流数字型彩票模型：
  - **X+Y 模型**：从普通号码池选择 X 个普通号码，再选择 Y 个特别号码。例如普通号码 `1,2,3,4,5,6`，特别号码 `7`。具体号码范围、是否允许重复、普通号码与特别号码的号码池规则待确认。
  - **M 选 N 模型**：M 是非 0 正整数，N 小于 M；总选择数 N 拆分为 `N = N1 + N2`，其中 N2 是特别号码。普通号码和特别号码需要分别定义选择规则和中奖判断规则。
  - **0~9 N 位数字模型**：号码取值为 `0~9`，N 表示数字位数；是否允许重复由具体玩法配置决定，例如三位结果可以是 `121` 或 `111`。
- X+Y 模型支持衍生玩法：每个号码可以配置一个或多个附加属性。
- 支持排除玩法，例如排除号码 `1,2,3`，系统不得在生成或确认投注组合中使用这些号码。
- 支持复式玩法，根据玩家选择的多个号码生成符合规则的投注组合。
- 支持倍投玩法，按照传统算法按倍数放大投注金额和对应中奖结算值。
- 支持基于开奖结果特征的规则，例如：
  - `111`：三个号码相同；
  - `121`：首尾号码相同；
  - 按每个号码的奇数/偶数属性判断；
  - 后续可扩展和值、大小、连续号、重复号、跨度等特征。
- 玩法规则、号码属性和开奖特征需要采用可配置的规则模型，避免为每个玩法单独硬编码一套结算逻辑。
- 衍生玩法数量不可预先穷举，系统必须支持通过规则配置动态添加和调整衍生玩法，常规新增玩法不应依赖修改核心代码。
- 玩家如何选号、提交订单和查看开奖结果。
- 开奖频率、开奖时间和时区。
- 奖级、中奖判断和奖金计算规则。
- 是否支持多种彩票或多个游戏房间。
- 开奖结果来源：人工录入、外部官方接口、第三方结果源，或系统生成。
- 是否需要可验证的随机数、审计日志或开奖证明。
- 第一期支持配置多个外部开奖结果源，并支持人工补录。

### 4.1.1 通用玩法引擎方向

- **号码池**：定义号码范围、普通号码池、特别号码池、分组和是否允许重复。
- **选择规则**：定义玩家需要选择的号码数量、顺序要求和特别号码要求。
- **号码属性**：允许为一个号码绑定多个属性，例如奇数/偶数、大小、颜色或客户定义属性。
- **组合规则**：支持普通选择、排除、复式和倍投等投注方式的组合。
- **结果特征**：对开奖结果生成可查询的特征标签，用于奖级判断和衍生玩法。
- **中奖规则**：根据投注内容、开奖结果、附加属性和结果特征计算命中情况。
- **结算规则**：根据奖级、倍数和积分规则生成结算结果，并交给积分账本和派奖流程处理。
- **玩法驱动的中奖判断**：是否中奖由注单绑定的具体玩法规则决定。例如某玩法只要求匹配特别号码时，用户选择的特别号码与开奖结果一致即可中奖。
- **玩法赔率**：赔率或中奖积分计算方式配置在对应玩法中，并随注单保存玩法规则版本。
- **规则版本**：每个游戏和期次必须保存当时使用的规则版本，避免后续修改配置影响历史订单结算。
- **动态规则**：衍生玩法通过规则定义、条件组合和结算配置添加，规则引擎负责解释和执行。
- **规则组件**：规则应由可复用组件组成，例如号码选择、排除条件、号码属性、位置关系、奇偶判断、和值、范围、重复关系、倍数和奖级。
- **规则表达能力**：需要支持条件、组合、嵌套条件、优先级和结算动作，以覆盖当前未知的衍生玩法。
- **运营配置**：运营人员应能通过后台可视化界面创建和配置常规衍生玩法，减少对程序员开发和沟通的依赖。
- **组件化编辑器**：规则编辑器使用预置规则组件、条件组和结算动作，运营人员通过选择、填写参数和组合条件完成配置，不直接编写程序代码。
- **规则模板**：提供 X+Y、M 选 N、0~9 N 位数字、排除、复式、倍投、奇偶、和值、重复号和位置关系等常用模板，支持复制已有规则后修改。
- **投注限额**：单注限额、单期限额和用户限额均采用配置方式，并按适用品牌、彩种、玩法或用户范围生效。
- **规则校验**：发布前检查号码范围、条件冲突、奖级冲突、结算结果和边界情况。
- **规则预览**：后台可以用指定开奖结果和测试投注模拟规则，查看命中结果、奖金或积分结算结果。
- **规则审核**：规则创建、修改、启用、停用和回滚需要权限控制，并记录操作审计。
- **强制审核**：运营人员创建或修改的规则必须经过审核，审核通过后才能发布或生效。
- **职责分离**：规则创建者不能审核自己创建或修改的规则；审核人需要具备相应品牌或平台权限。
- **审核角色**：具体规则由所属品牌的品牌管理员审核；平台超级管理员可以跨品牌查看规则和审核记录，但不参与具体规则审核。
- **审核重点**：审核玩法漏洞、条件冲突、不可达奖级、重复命中、边界条件、中奖覆盖范围以及赔率或积分回报是否合理。
- **审核材料**：提交审核时必须附带规则配置、规则版本、测试投注、测试开奖结果、命中明细和预期结算结果。
- **审核结果**：支持通过、驳回、退回修改和要求补充说明，并记录审核意见。
- **生效保护**：未审核、审核驳回或已过期的规则不能用于新订单；已生效规则修改后生成新版本，不直接覆盖历史版本。
- **生效方式**：审核通过后支持配置两种生效方式：
  - **立即生效**：审核完成后立即用于符合条件的新投注；已创建订单继续使用原规则版本。
  - **下期生效**：审核完成后不影响当前投注周期，从下一个新的投注周期开始使用新规则版本。
- 生效方式、审核完成时间、生效时间、生效期次和规则版本必须写入审计记录。
- **生效范围**：规则可以按平台、品牌、游戏或期次配置，并支持设置生效时间或生效期次。
- **游戏期次**：投注周期由所属彩票种类配置，不采用平台统一周期；支持每天一次、每固定分钟间隔一次等调度方式。
- **期次状态**：每个期次应有待开始、投注中、已截止、待开奖、已开奖、结算中和已结算等状态，具体状态集合待确认。
- **下期生效计算**：选择“下期生效”时，系统根据规则所属游戏的开奖频率和当前期次状态，自动绑定审核完成后的下一个可投注期次。
- **规则冻结**：订单创建或期次开始后，必须绑定当时生效的规则版本，后续规则修改不能改变已产生订单的结算结果。

### 4.1.2 期次与开奖计划

已提出的期次字段：

- 期次编号；
- 品牌编号；
- 彩种编号；
- 期次名称或期次序号；
- 投注开始时间；
- 投注截止时间；
- 开奖时间；
- 开奖频率，包括忙时和闲时；
- 暂停日期；
- 节假日规则。

建议补充的字段和能力：

- **时区**：明确时间字段使用的时区，支持品牌或彩种设置时区，系统内部统一使用 UTC 保存时间。
- **期次状态**：标准流程为待开始、投注中、已截止、待开奖、已开奖、结算中、已结算；取消分为投注取消和判定取消。
- **标准状态流转**：`投注中 → 已截止 → 待开奖 → 已开奖 → 结算中 → 已结算`。
- **相邻期次开放边界**：同一品牌、同一彩种，上期截止投注后必须完成整期结算，才能开始下一期投注；已开奖、计算完成或审核通过不代表可以开放下一期。异常注单按既定排除规则成为终态，全部目标终结且期次已结算后才放行。
- **取消后的下一期**：上期整期取消时，必须等待全部原路退款完成；取消任务处理中或失败时不得开放下一期。
- **结算拖延**：下一期仍在原定投注窗口内才可开放；原窗口已过则跳过，按日历进入后续有效期，不改写旧时间、补开或延长窗口。预生成待开始期次不等于已经开放投注。
- 每次状态变化必须记录变化时间、触发方式、操作主体和关联规则/开奖结果/结算记录。
- **取消状态**：投注取消用于投注阶段取消期次或投注；判定取消用于根据开奖、规则或运营判定取消期次或相关结算。
- **投注取消触发**：是否允许用户在开奖前取消注单，由品牌/彩种配置决定；允许时还需受注单状态和配置的取消时点约束。
- 运营人员发现异常注单后，可以随时取消该异常注单；系统必须记录取消原因、异常依据、操作人和操作时间。
- **判定取消触发**：本期没有开奖结果，或开奖结果被判定为异常时，可以对期次或相关注单执行判定取消。
- **取消退款**：期次取消或注单取消时，涉及的投注积分全额按原积分来源、原金额和原状态原路退回，并生成独立退款流水。
- **异常注单**：原“异常待处理”统一命名为“异常注单”，用于标识订单数据、规则判定、开奖关联或积分结算出现异常、需要人工处理的注单。
- 被人工判定为异常的注单不参加重新结算；可以由授权运营人员人工判定异常及处理结果，但不能通过普通重试流程自动派奖。
- **规则版本编号**：记录本期使用的玩法规则版本，确保期次和订单可以还原当时规则。
- **开奖来源类型**：平台自开奖、外部结果源或人工补录，并记录对应来源配置。
- **外部结果源**：支持为彩种配置多个外部结果源，并保存来源名称、接口地址、认证配置、优先级、启用状态和适用期次范围。
- **结果选择策略**：第一期采用主来源加多个备用来源，按优先级切换；暂不进行多来源结果比对。
- **人工补录**：外部结果缺失、冲突或异常时允许授权人员补录；第一期不要求双人复核，但必须填写原因、来源说明并完整记录原结果、修改后结果、操作人和操作时间。
- **结果锁定**：开奖结果确认并进入结算后不能直接修改；需要修改时必须走纠正或重开流程，并保留原结果、修改原因、操作人和操作记录。第一期不要求双人复核。
- 第一期结果源采用“主来源 + 多个备用来源”的优先级链路，按配置顺序获取结果。
- 第一期暂不进行多个来源之间的结果比对或共识确认。
- 主来源或当前来源出现超时、接口错误、无数据或数据异常时，系统按优先级自动切换到下一个可用来源。
- 每次来源切换必须记录失败类型、失败时间、来源编号、重试次数和切换结果。
- 人工录入开奖结果后，本期立即锁定人工结果，不再继续请求或采用其他外部来源。
- 人工录入后的本期结果来源标记为人工录入，并记录操作人、原因、时间和审核信息。
- 外部开奖失败或没有可用结果时，授权运营人员可以执行人工开奖；人工开奖需要填写原因、开奖结果来源说明并保留完整审计记录。
- 开奖结果纠正时允许重新结算；重新结算前必须回溯原结算产生的全部业务数据，包括中奖积分、派奖流水、佣金/奖励、流水统计和相关通知状态。回溯不得删除原记录，应通过冲正、撤销或反向流水保留完整审计链，然后使用纠正后的开奖结果重新结算。
- 外部开奖结果需要执行异常校验：
  - 期数与当前待开奖期次不一致；
  - 号码数量与彩种规则不符；
  - 号码超出彩种允许范围；
  - 开奖号码与上一期完全相同。
- “与上期完全相同”属于统计上极低概率但理论可发生的高风险异常，默认触发异常处理或切换来源，不直接判定为绝对无效结果。
- 每项异常校验需要记录校验规则版本、校验输入、异常类型、处理结果和来源信息。
- 外部结果源适配两种接入方式：API 接口和外部网页 DOM 抓取。
- 第一期暂不实现具体 API 请求逻辑或网页 DOM 抓取逻辑，使用伪实现、模拟响应和测试数据完成接口联调。
- 两种接入方式统一实现开奖结果源适配器接口，输出统一的标准化结果结构，再进入期数匹配、异常校验和结果锁定流程。
- 适配器需要预留请求超时、错误、无数据、数据异常、重试和来源切换的返回状态。
- DOM 抓取适配器需要将页面定位规则作为来源配置的一部分，具体选择器和网页解析逻辑后续再实现。

#### 开奖结果记录

开奖结果记录字段：

- 结果编号；
- 品牌编号；
- 彩种编号；
- 期数；
- 开奖号码，使用 JSONB 格式，同时支持 X+Y、M 选 N 和 0~9 N 位数字模型；
- 开奖时间；
- 来源编号；
- 创建时间。

建议补充字段：

- **结果状态**：已接收、校验中、异常、待人工确认、已确认、已锁定、已撤销或已纠正。
- **来源类型**：API、DOM 抓取或人工录入。
- **规则版本编号**：记录结果校验时使用的彩种规则版本。
- **校验信息**：校验时间、校验结果、异常类型和校验详情。
- **原始数据引用**：保存原始响应或页面数据的存储引用；不便直接保存时至少保存摘要和哈希值。
- **确认信息**：确认人、确认时间、确认原因和审核记录。
- **修改信息**：纠正前结果、纠正后结果、修改原因和审批记录。

JSONB 建议使用统一外层结构，并由模型字段区分具体号码结构，例如：

```json
{
  "model": "X_PLUS_Y",
  "regular": [1, 2, 3, 4, 5, 6],
  "special": [7],
  "attributes": {}
}
```

```json
{
  "model": "M_SELECT_N",
  "poolSize": 49,
  "totalSelected": 7,
  "regularCount": 6,
  "specialCount": 1,
  "regular": [1, 2, 3, 4, 5, 6],
  "special": [7],
  "allowRepeat": false,
  "attributes": {}
}
```

```json
{
  "model": "DIGITS_0_9",
  "digits": [3, 1, 0],
  "allowRepeat": true,
  "attributes": {}
}
```

原先的“M×N”称法不准确。针对这类数字模型，需要区分两类：一是 M 选 N，其中 M 是非 0 正整数、N 小于 M，且 `N = N1 + N2`，N2 为特别号码；二是 0~9 N 位数字模型，其中号码取值为 `0~9`，N 表示位数，是否允许重复由玩法配置决定。后者可以表示 `310`、`121`、`111` 等结果。

具体 JSONB 字段名称和附加属性结构仍需结合最终彩种规则确认。
- **开奖结果状态**：未生成、待确认、已确认、被驳回和重新处理。
- **结算状态**：未结算、结算中、部分完成、已完成、失败待处理。
- **期次唯一键**：由品牌、彩种和期次序号组成唯一约束，防止重复生成期次。
- **生成方式**：系统自动生成、运营人员手动生成或外部计划导入。
- **投注截止缓冲时间**：开奖前预留锁盘、订单同步和风控处理时间。
- **开奖时间窗口**：允许开奖延迟、重试或人工接管的时间范围。
- **暂停和恢复原因**：记录暂停类型、原因、操作人、开始时间、恢复时间和影响期次。
- **取消或顺延规则**：开奖失败、外部结果缺失、节假日或系统故障时，定义取消、顺延、退款和重新开奖方式。
- **调度计划版本**：忙时、闲时、周末和节假日计划修改后生成新版本，已生成期次继续使用原计划快照。
- **审计字段**：创建人、创建时间、最后修改人、最后修改时间和操作日志。

开奖频率建议使用时间段计划表达，例如：

- 时间段：`00:00-08:00`，每 30 分钟一期；
- 时间段：`08:00-23:00`，每 10 分钟一期；
- 节假日：暂停生成或使用特殊频率；
- 每个计划需要明确开始日期、结束日期、时区和优先级。
- **失败保护**：规则执行失败、规则缺失或结果无法确定时，系统不得自动完成派奖，应进入异常处理流程。
- **人工扩展通道**：超出规则组件能力的特殊玩法进入需求评估，由程序员增加通用组件后，再交给运营人员配置具体规则。

### 4.12 用户账户与品牌关系

- 用户可以属于多个品牌。
- 用户可以通过品牌域名、代理码或推荐码加入对应品牌。
- 品牌运营人员可以在管理端新增用户并建立品牌成员关系。
- 品牌成员关系需要记录加入方式、品牌域名、代理码、推荐码、邀请来源、加入时间和创建人。
- 代理关系和推荐关系在用户成功加入品牌后需要保存快照，后续修改编码不能改变历史归属和相关业务记录。
- 品牌支持代理层级关系；代理层级数量、上下级关系和是否允许继续发展下级由品牌配置。
- 品牌可以配置代理佣金规则和推荐奖励规则，包括适用彩种、计算基数、比例或固定金额、发放条件和生效时间。

- 代理佣金和奖励配置修改后生成新版本，历史注单和已产生的佣金记录继续使用原规则。
- 代理层级、佣金和奖励的配置、审核、启用、停用和人工调整需要权限控制和审计记录。

### 4.13 后台账号、角色与权限

- 后台账号是登录主体，角色是权限集合，权限是最小可授权操作单元。
- 权限建议按“资源 + 操作 + 范围”表达，例如：`withdrawal.approve.brand`、`rule.review.brand`、`user.view.platform`。
- 资源包括用户、品牌、彩种、玩法规则、期次、注单、开奖结果、积分账本、提现、报表和审计记录。
- 操作包括查看、创建、修改、删除、提交、审核、批准、驳回、取消、导出和执行。
- 范围包括平台级、品牌级和本人/本人创建数据等，具体范围按业务需要配置。
- 账号拥有多个角色时，权限取并集并去重；撤销任一角色后，系统重新计算账号最终权限。
- 权限变化应支持立即生效，并使已失效的后台会话重新校验权限。
- 角色不能绕过品牌数据隔离；平台级查看权限也不自动代表拥有修改权限。
- 对提现批准、规则审核、积分人工调整、结果人工录入、人工开奖和开奖结果纠正等高风险操作，需要单独权限和完整审计；第一期不要求双人复核，但所有记录必须支持按条件查询。

### 4.14 代理层级、佣金与奖励

- 品牌支持代理体系，代理层级、上下级关系、层级深度以及是否允许代理继续发展下级，均由品牌配置。
- 用户通过代理码或推荐码加入品牌时，需要建立对应的代理归属或推荐关系，并保存历史归属快照；后续修改编码或层级关系不能改变已经产生的历史业务记录。
- 品牌可以配置代理佣金规则和推荐奖励规则，包括适用品牌、彩种或玩法、计算基数、比例或固定金额、适用层级、发放条件、生效时间和失效时间。
- 品牌管理员可以为品牌配置代理佣金比例以及佣金计算模式；第一期支持按“输赢”或“流水”计算，具体模式作为佣金规则版本的一部分保存。
- **输赢模式**：只对代理名下用户产生的有效输钱注单计佣；投注结果为用户中奖、平局或其他不构成用户输钱的结果不计入。投注取消、异常注单和无效注单不计入，不能通过状态变更重复计佣。
- **流水模式**：按代理名下用户的有效投注流水计佣；投注取消、异常注单和无效注单对应的投注额从流水中扣除。具体有效流水金额以注单最终结算结果和关联规则版本为准。
- 佣金结算周期由品牌配置为按周结或按月结；符合条件的佣金按周期进入结算处理，周期边界、结算日和结算时间需要作为品牌配置保存。
- 多级佣金采用差额分配，不采用各层独立全额发放。同一计佣基数100、上级10%、下级6%时，上级4、下级6。下级的有效计佣模式必须与直接上级一致，不支持同一路径混用输赢/流水模式；沿用上级或显式填写相同模式均可。根代理没有上级代理时，可沿用品牌默认或由品牌管理员设置模式。
- 佣金不在每个彩票期次结算时生成待结佣金；在周/月佣金周期结算流程中批量计算。周期边界以及人工审核派发或系统自动派发由品牌配置，不固定为周一/月初或强制人工。
- 周期结束后，等待该周期所有注单最终完成后再结佣；未完成注单不能按零额排除，也不移入后续周期。取消/异常等最终排除状态仍保留证据，不产生佣金。
- 每个代理的周期差额佣金先精确累加，最后统一四舍五入为整数积分；不逐注、逐层提前舍入。例如两笔0.3合计0.6，周期佣金为1，而非0。
- 代理停用只限制代理操作，不停止计佣；新旧投注均按各自投注时不可变快照计佣，不因当前节点停用而排除。
- 0049自动发现已到期周/月窗口，按投注时日历登记核算周期，不使用当前配置补造历史规则；系统和人工登记去重、可查询失败并人工重试。系统登记不代表审核或佣金派发。
- 后台佣金页已接入真实周期、发现队列、当前汇总及代次轨迹，支持有权限的品牌管理员登记及重试；独立派发页提供运行开关、单人审核和失败重试。未知写入须原键原正文恢复，当前状态与原始回执分别展示，不显示虚构已派发金额；奖励仍另行实现。
- 佣金派发进入新增的独立“佣金积分”来源，不归入中奖或赠送积分。佣金积分可以投注，扣除顺序为充值→中奖→佣金→赠送；佣金可用余额不计入提现流水门槛基数，使用佣金支付的有效投注仍计入有效流水。0050将完整当前核算代次审核及真实账本入账接入；核算ready不代表已派发，实际进度须查询派发任务和目标流水。
- 派发运行开关默认关闭，品牌管理员显式开启后，已有核算就绪且未派发的历史周期也按各自保存模式处理。全人工须品牌单人审核，全自动由系统授权；混合周期整期人工审核，不拆分自动部分，不以当前政策覆盖历史快照。0054保留mixed身份，旧MODE_UNRESOLVED阻止记录只能在无批准、无目标且当前证据有效时显式人工批准，不由升级或工作器自动恢复。关闭只暂停后续入账，不撤销既有批准或积分。
- 更正发生前无正额入账时旧任务保留为stale，新代次另行审核；已有正额入账时停止该周期后续发放并保留blocked原任务，不以新总额二次全额派发。0059在独立默认关闭的资金开关下接入内部差额补发、追回、单人批准及技术重试。追回只扣可用佣金，不足则暂停整周期，暂停跨新核算保留；运营处理后显式继续，不扣其他来源、自动解冻或形成负余额，余额补足也不自动恢复。新计划按已经实际授予的净额计算，包括旧补偿部分执行的金额；管理接口、双端操作、补偿通知和报表继续实施，见[执行合同](23-commission-correction-execution.md)。
- 代理可以在品牌允许的范围内为自己的下级代理设置佣金比例，但下级代理比例不得超过当前代理自身可分配或已配置的佣金比例；系统保存上级比例、下级比例和当时的配置链路。

- 佣金和奖励配置必须版本化；历史注单、期次和已经产生的佣金记录继续使用原规则，不能因后续配置修改而重新计算。
- 代理佣金与推荐奖励需要作为独立业务记录和积分流水处理，并关联品牌、代理、被推荐用户、注单、期次、规则版本、配置版本和积分变动。
- 佣金与奖励的生成、待结算、结算、撤销、人工调整和异常处理需要有明确状态，并支持幂等，避免重复发放。
- 第一期奖励仅实现后台人工奖励订单及撤销，不实现自动代理、推荐或活动奖励。原赠送可用积分不足以撤销时保留人工待处理，运营处理后显式继续；不得扣其他来源、自动解冻或形成负余额，余额补足不自动恢复。0055接入独立订单、全额反向原账本、动作历史、管理接口及客户端；后台双语页面及PC/360px真实浏览器资金流程已接入并验证。0056接入发放、撤销待处理和已撤销的不可变站内通知，待处理说明本次没有积分变动，原键重放不追加事件。0057接入实际入账与按订单创建时间筛选的当前状态两种报表、独立查看/导出权限、完整CSV和工作台状态计数；查询不改积分。通用积分调整不代替订单及撤销历史，报表不等于封存日月结；详细口径见[奖励报表合同](21-reward-reports.md)。
- 0051/0052对当前已paid且证据有效的佣金目标追加独立人工差额修正与真实入账通知：原核算/批准/派发金额和流水保留；只移动可用佣金来源，余额不足不扣其他来源。原回执与当前净额分开展示，全部前后积分、原因、人员及审计可追溯。该修正不解锁结果更正blocked；0059另以新批准和执行任务处理结果更正，原人工修正后再更正的OPEN-117组合仍整期阻止，见[修正交接合同](18-commission-adjustments.md)。
- 0053补充实际佣金账本报表和完整CSV：按真实ledger入账时间、品牌时区日/原代理/周期分组，支持会员筛选；原派发和正负修正分别统计、只计一次。区间负净变动不代表负佣金或负余额；报表不代替未派发应付、按投注归属核算或封存日月报。独立查看/导出授权及审计、精确字符串和双端查询/下载契约见[报表交接合同](19-commission-posting-reports.md)。
- 佣金金额最低为 0，不产生负佣金；授权人工可以修正佣金，但不能覆盖或删除原始计算记录，必须通过独立调整记录保存修正前后金额、原因、操作人和审批信息。
- 代理层级、佣金和奖励的创建、修改、审核、启用、停用、结算和人工调整需要权限控制及完整审计；高风险人工调整应记录原因和原审批信息。
- 注单按投注时间归属佣金周期，边界采用开始含、结束不含；跨周期才结算或更正的注单仍归原投注周期，不按结算时间迁移。未最终结算的注单不能按零佣金忽略；完整周期收尾、补结、失败重试和人工调整审批流程仍需落实，不改已确认的时间归属口径。

### 4.15 技术架构与 UI 方向

#### 总体架构

- 第一阶段采用模块化单体架构，按领域拆分模块，暂不拆分为多个独立微服务；通过异步任务和事件机制处理开奖抓取、结算、通知、佣金计算和报表任务。
- 用户端和管理端采用两个独立前端项目，后端提供统一 API、权限校验和品牌上下文；基础 UI 组件、类型定义和多语言资源可以通过共享包复用。
- 业务模块至少包括全局身份、品牌与成员、彩种与玩法、期次与开奖、注单、结算、积分账本、充值、提现、代理佣金、通知、报表和审计。

#### 推荐技术栈

- 后端优先采用 Go，适合高并发请求、开奖任务、结算任务和长时间运行的后台服务；外部接口使用 REST/OpenAPI，内部异步任务使用统一事件模型。
- 用户端和管理端优先采用 Vue 3 + TypeScript + Vite，分别构建独立应用；共享品牌主题、表单、表格、权限指令和多语言组件。
- 主数据库采用 PostgreSQL，使用 JSONB 保存玩法规则、选号内容和开奖结果；积分账本、注单、提现和结算数据使用强事务模型。
- 缓存和并发辅助采用 Redis，用于会话、限流、热点配置、幂等辅助和短期状态；不能把 Redis 作为积分账本的唯一事实来源。
- 异步任务采用“数据库事务 + Outbox + 消费者”模式，第一期可使用轻量消息队列，后续根据吞吐量扩展到高可靠消息集群。
- 原始开奖响应、品牌素材、导入文件和报表文件保存到对象存储，不直接依赖业务数据库保存大文件。

#### 高并发与数据一致性

- 数据库采用一主多从，并配置主库高可用切换；所有积分、投注、提现、结算和配置写入只进入主库。
- 读请求按业务类型路由：用户余额、订单刚提交后的结果、提现状态和后台审核结果优先读取主库；历史列表、报表和统计查询可以读取从库。
- 需要读后写一致的场景使用主库粘滞、版本号或时间窗口，不能让用户刚完成的操作因从库延迟而显示旧数据。
- 注单提交、余额扣减、账本流水和提现冻结必须在同一事务内完成，并结合幂等键、数据库锁和唯一约束防止重复处理。
- 彩种配置、玩法规则和品牌配置使用缓存，但配置发布后必须主动失效缓存，并保留版本号。
- 结算、佣金和报表任务按品牌、彩种或期次分片执行，避免单个大任务阻塞全部品牌。
- 通过连接池、限流、熔断、超时、重试和降级保护数据库及外部开奖结果源。

#### UI 与终端策略

- 用户端采用移动端优先、同时适配桌面浏览器的响应式 PWA 设计；管理端同时支持 PC 和移动端，桌面端提供完整配置能力，移动端重点覆盖监控、审核、查询和应急操作，复杂玩法配置优先保留在桌面端。
- 支持品牌独立 Logo、颜色主题、域名、语言、首页模块和功能开关；未配置时继承平台默认主题和内容。
- 用户端重点页面包括登录注册、游戏大厅、选号、投注确认、注单、开奖结果、积分、充值、提现、中奖记录和通知。
- 管理端重点页面包括工作台、用户、代理、彩种玩法、期次开奖、注单异常、积分充值、提现、佣金奖励、报表、权限和审计。
- 玩法配置采用向导和可视化规则组件，支持预览、模拟投注、模拟开奖、审核、发布和版本回滚。
- 第一阶段需要制作可交互 UI 原型，优先覆盖登录、游戏大厅、选号投注、订单、钱包提现、管理工作台、玩法配置和审核流程。
- 所有页面需要统一处理加载中、空数据、错误、权限不足、网络超时、重复提交和品牌暂停等状态。

#### 性能目标

- 第一阶段容量目标按峰值约 500 名在线用户、每秒约 500 次投注请求设计。
- 投注、积分扣除、注单创建和幂等校验需要在高并发下保持事务一致性，不能因为读写分离或缓存导致重复扣款。
- 需要通过压力测试验证投注接口、余额接口、期次接口、开奖任务和结算任务，并为数据库连接池、主库写入、队列堆积和缓存命中率设置监控告警。
- 具体接口延迟目标、峰值持续时间、故障恢复时间和容量余量待在技术验收标准中确认。

#### 还需确认的架构与 UI 事项

- PC 和移动端是统一响应式网页/PWA，还是需要提交 iOS、Android 和 HarmonyOS 原生应用；操作系统浏览器支持不等同于应用商店原生支持。
- 管理端移动端是提供完整功能，还是重点支持查询、审核和应急操作；复杂规则编辑通常保留在桌面端。
- 第一阶段预计用户量、峰值并发、每秒投注请求量、品牌数量和数据保留年限。
- 是否需要多地域部署、自动故障切换、灾备机房和明确的恢复时间目标。
- 是否已有品牌 Logo、颜色、字体、语言文案和设计规范；没有时需要先建立平台设计系统。

### 4.3 账户与资金

- 首期包含账号、充值、提现和奖金发放。
- 首期不接入真实支付服务；充值采用后台人工创建和确认的单人流程，提现先通过内部处理流程完成状态流转。
- 平台内部账户余额和业务结算统一使用平台积分。
- 积分模型区分“余额状态”和“积分来源”：余额状态表示积分当前能否使用，积分来源表示积分从哪里产生。
- 各类积分的转移必须通过账本流水记录，不能直接覆盖余额数值。
- 未来支付接入支持法定货币或虚拟资产到平台积分的转换；具体支持哪些资产仍需确认。
- 钱包由客户、持牌支付机构还是第三方托管。
- 充值、提现、退款、撤单和人工审核规则。

### 4.6 多语言与积分

- 用户端和后台支持多语言。
- 语言可以按平台设置，品牌可以选择或覆盖可用语言。
- 平台内部统一使用积分作为账户和游戏结算单位。
- 法币或虚拟资产的支付金额不直接进入游戏业务模块，由支付层转换为积分后再进入账户账本。
- 积分与法币/虚拟资产的兑换比例、汇率来源、锁定时间、精度、舍入、手续费和退款规则待确认。

### 4.7 积分模型

积分账户采用“状态 + 来源”的双维度模型。来源分类不额外增加一份余额，避免同一笔积分被重复统计。

#### 余额状态

- **显示积分**：用户账户展示的积分总额，由可用积分和冻结积分组成。
- **可用积分**：可以参与彩票游戏或执行其他允许操作的积分。
- **冻结积分**：暂时不能使用的积分，由人工冻结或系统冻结组成。
- **提现积分**：用户提交提现申请后，已从可用积分中转出，等待管理员或系统审核处理的积分。提现积分不计入显示积分，账本中必须单独记录，并可在提现记录或账户明细中查看。

#### 积分来源

- **充值积分**：来源为用户充值转换得到的积分。
- **中奖积分**：来源为彩票中奖结算得到的积分；中奖积分属于可用积分的一种来源。
- **赠送积分**：来源为运营活动、管理员操作或其他允许渠道发放的积分；赠送积分属于可用积分的一种来源。
- **佣金积分**：来源为代理佣金周期派发，独立标记，不与中奖或赠送来源混用。可投注，采用相同余额状态及前后流水追溯模型，不计入提现流水门槛基数；0046已支持此独立积分来源，0048已保存周期收益核算；审核和派发仍需单独实现，核算完成不代表积分入账。

#### 状态变化

- 充值积分、中奖积分、赠送积分和佣金积分在有效入账后进入各自的可用状态，积分只保留整数，不支持小数；可用状态本身不替代各来源的业务使用授权。
- 可用积分可以根据订单、风控或审核流程转为冻结积分；冻结原因区分人工冻结和系统冻结。
- 冻结积分解除冻结后返回可用积分，并保留原积分来源；被扣除、作废或调整时必须生成对应流水。
- 用户提交提现申请后，符合规则的积分从可用积分转入提现积分。
- 提现审核通过并完成处理后，提现积分转为已完成状态；审核拒绝或提现失败时，按规则退回可用积分或进入人工处理。
- 所有状态变化必须生成可追溯的积分账本流水，并关联品牌、用户、订单、活动、冻结记录或提现申请。

#### 建议补充

- 每笔积分应记录来源类型、来源单号、当前状态、变动金额、变动前后余额、创建时间和操作主体。
- 每笔积分流水必须保存变更前和变更后的积分值，用于完整还原余额变化过程。
- 余额快照至少包括显示积分、可用积分、冻结积分和提现积分；涉及来源拆分时，同时保存充值、中奖、赠送和佣金积分的变更前后数值。旧三来源历史不得覆盖改写，四来源账本的升级和兼容需单独验证。
- 积分流水应记录变更原因、业务类型、关联业务单号、操作主体、操作时间和请求或幂等标识，便于定位重复提交和异常变更。
- 积分流水应采用追加记录，余额可以通过流水汇总或经过校验的余额快照得到。
- 系统冻结和人工冻结应使用不同原因码，并记录解除时间、操作者和审核信息。
- 充值积分、中奖积分、佣金积分和赠送积分均不过期；提现允许来源、额度和审核仍按品牌配置校验。
- 投注扣减顺序为充值积分→中奖积分→佣金积分→赠送积分，退款不采用此顺序重分配，而是按原扣款分配返还。
- 需要定义提现失败、订单取消、派奖撤销和管理员冲正时的积分回退规则。
- 注单扣除积分时必须保存实际使用的积分来源和金额，包括充值、中奖、佣金和赠送各自扣除多少。
- 注单取消时，积分必须按原扣除来源、原扣除金额和原积分状态原路退回，不能只增加一笔未区分来源的可用积分。
- 原路退回必须关联原注单和原扣分流水，并生成独立的退回流水，保留完整的前后余额快照。
- 如果原积分来源已经过期、被限制或发生其他状态变化，取消流程进入异常注单或人工处理，不得静默改变退回来源。

### 4.8 注单流程

#### 投注阶段

- **选号**：用户根据游戏规则选择号码、附加属性和衍生玩法条件。
- **确认**：系统校验选号是否合法，计算复式展开结果、注数、倍数和总积分，并展示给用户确认。
- **投注**：用户提交最终投注请求，系统校验期次仍在投注中、规则版本有效、账户可用积分足够，然后扣除积分并创建注单。
- **取消**：是否允许用户在开奖前取消由品牌/彩种配置决定；允许取消时，需要明确取消范围、可取消注单状态和是否允许部分取消。
- 运营人员发现异常注单后可以随时取消；取消操作需要填写原因，并按异常处理权限执行。
- 判定取消用于本期没有开奖结果或开奖结果异常等情况，可以作用于期次或相关注单。
- 期次取消或注单取消成功后，涉及积分全额按照注单保存的积分来源、金额和状态原路退回，并生成独立退回流水；不收取取消手续费。

#### 注单提交要求

- 注单必须保存品牌、用户、彩种、期次、投注内容、展开组合、附加属性、倍投倍数、规则版本、单注积分和总积分。
- 注单还必须保存积分扣除分配明细，包括每种积分来源的扣除金额、扣除前后状态和对应积分流水。
- 注单提交时保存选号原文和规则计算后的标准化结果，便于复核和审计。
- 扣除积分、写入积分流水和创建注单必须具备原子性；任一步骤失败时整体回滚，不能出现已扣积分但没有注单，或已有注单但未扣积分。
- 每次提交请求需要携带幂等标识；相同幂等标识重复提交时返回第一次请求的结果。
- 不同幂等标识不能因为网络重试生成相同的重复注单，需根据业务规则进行重复投注检查。
- 注单创建后绑定期次、规则版本和积分扣除流水，后续规则修改不能影响该注单。
- 注单取消后绑定原注单、取消原因、取消规则版本、退回分配明细和退回流水。
- 期次截止、账户余额不足、规则版本失效、重复提交或系统异常时，投注请求不得部分成功。

#### 订单与期次状态矩阵

- 期次正常流程为：`投注中 → 已截止 → 待开奖 → 已开奖 → 结算中 → 已结算`。
- 用户取消：品牌/彩种配置允许且注单仍满足开奖前取消条件时，注单进入投注取消并全额原路退款。
- 运营取消异常注单：运营人员发现异常注单后可以随时取消，记录异常原因、取消原因和操作审计。
- 判定取消：没有开奖结果，或开奖结果异常时，期次或相关注单可以进入判定取消，并全额原路退款。
- 异常注单：人工判定为异常的注单不参加重新结算；本期其他正常注单仍可继续结算，异常注单保留人工处理记录。
- 品牌暂停：暂停配置生效后立即禁止新投注；用户仍可登录和提现，已有注单、开奖和结算流程继续执行。
- 开奖失败：没有可用外部结果时，授权运营人员可以人工开奖，完成后进入已开奖及后续结算流程。
- 开奖结果纠正：允许在授权流程下纠正结果并重新结算；重新结算前先回溯原结算产生的派奖、积分、佣金/奖励、流水统计和通知等数据，再使用新结果重新结算。原始记录不得删除，必须保留冲正和重算链路。

### 4.9 提现流水规则

- 提现规则属于品牌级配置，由品牌管理员配置和维护，并经过相应审核后生效。
- 投注流水倍数 N 支持品牌级默认配置和彩种级配置。
- 品牌管理员可以配置品牌默认 N 倍值。
- 彩种可以单独配置 N 倍值；彩种配置优先于品牌默认配置。
- 彩种未配置 N 倍值时，继承所属品牌的默认配置。
- 充值积分和赠送积分需要完成品牌配置的 N 倍有效投注流水后，才满足提现条件。
- 提现流水门槛基数为当前品牌申请提交时、积分占用前的全部可用充值积分与全部可用赠送积分之和；不是本次申请中的来源金额，不包含中奖、佣金、冻结或已占用的提现积分。
- 该基数是当时的可用余额，不是累计充值/赠送本金；应在服务端锁定钱包后读取并保存快照，不能先扣除申请金额再降低基数。
- N 必须大于 0，不允许新增或修改配置为 0；彩种未配置时继承品牌默认 N，不把 0 当作继承。
- 跨彩种按折算后累加计算：`达标额度 = Σ（每笔有效投注金额 ÷ 该笔投注时的有效 N）`，达标额度大于或等于全部可用充值＋赠送余额时满足流水门槛。同一彩种跨规则版本的投注也分别使用各自快照；相同 N 时等价于有效投注流水达到基数的 N 倍。
- 积分金额仍只保留整数，但折算和比较必须采用精确分数，不对每笔或每个彩种的贡献先行舍入。例如 100÷2＋250÷5＝100；1÷3＋2÷3＝1，不能逐笔截断成 0。
- 中奖和佣金积分不计入提现流水门槛基数，但充值、中奖、佣金、赠送四种来源支付的有效投注金额均计入有效流水；不因资金来源不同重复计数。
- 每次提现成功后，以该申请的提交时间作为本次流水周期截止点；下次从该提交时间之后开始计算，历史流水不删除或清空。
- 提现失败、驳回或取消时，不推进成功周期截止点，积分按原来源全额退回；同品牌会员没有进行中申请后才可重新申请，详见4.10。
- 有效投注流水应按实际成功投注金额计算；投注取消、判定取消、异常注单和无效注单不计入有效流水。测试注单和未完成订单默认不计入，具体测试规则另行配置。
- 每笔有效流水应关联品牌、用户、注单、投注金额、来源期次和计入时间，支持追溯和重新计算。
- 品牌管理员修改 N 倍规则或计算范围时生成新配置版本，仅影响新投注。每笔投注保存当时品牌/彩种规则版本、继承来源和有效 N 的不可变快照，资格计算不按申请时的新配置重算旧投注。
- 旧注单缺少投注时的规则快照时，不得补造历史 N；正式资格实现必须明确报告缺失证据并安全拒绝，不能凭当前配置放行。
- 品牌级和彩种级 N 倍配置都必须记录配置来源、优先级、版本、生效时间和操作审计。

### 4.10 提现流程

- 提现金额下限、提现金额上限和提现积分来源限制由品牌管理员配置。
- 提现审核模式由品牌管理员配置，支持运营人员审核、系统自动审核或按规则组合审核。
- 用户提交提现申请后，申请状态为**审核中**。
- 审核通过后，申请状态变为**提现中**。
- 运营人员批准或系统批准并完成提现后，申请状态变为**已提现**。
- 运营人员可以批准、驳回或取消提现申请，但不能修改已创建的提现记录。
- 驳回提现时必须填写驳回理由；取消、批准和驳回都必须记录操作人、时间和原因。
- 提现申请提交时，将符合条件的积分从可用积分转入提现积分，并保存积分来源分配明细。
- 提现成功后不删除或清空历史投注流水；本次提现作为投注流水计算周期的截止点。
- 下一次提现的投注流水从本次提现申请提交时间开始重新计算，历史流水继续保留用于审计和追溯。
- 提现失败或驳回时，提现积分按原积分来源、原金额和原状态退回对应积分字段，并生成独立退回流水。
- 同一用户同一品牌不允许存在多个同时进行中的提现申请；存在审核中或提现中的申请时，不得创建新的提现申请。
- 提现提交必须支持幂等处理，相同请求重复提交只能返回第一次申请结果，不能重复冻结积分或生成多个提现申请。
- 系统需要对用户和品牌建立进行中提现的唯一约束或等效并发控制，防止并发请求突破提现额度。
- 提现记录需要保存品牌、用户、申请金额、积分来源分配、当前状态、周期截止时间、审核记录、处理结果和关联积分流水。

### 4.11 中奖判断与结算

- 是否中奖由注单绑定的具体玩法规则决定，不采用脱离玩法的全局固定判断方式。
- 例如某玩法只要求匹配特别号码时，用户选择的特别号码与开奖结果一致即可中奖；具体命中条件由该玩法配置决定。
- 赔率或中奖积分计算方式配置在对应玩法中，并随注单保存玩法规则版本。
- 大多数玩法采用单一奖级，个别玩法支持多个奖级；奖级是否排他按玩法配置。
- 赔率、奖级、封顶值和舍入方式均由配置决定；积分结算采用四舍五入，具体精度和封顶值读取对应配置。
- 多个奖级同时命中时，根据奖级配置判断是否具有排他性：
  - 具有排他性时，按配置优先级选择应派奖级，默认优先金额较高的奖级；
  - 不具有排他性时，各命中奖级按规则累加。
- 复式和倍投按照传统方式计算，具体注数、倍数和中奖积分由对应玩法规则计算。
- 中奖积分属于可用积分，并保留“中奖积分”来源字段。
- 单个注单出现数据异常时，整个注单不参与结算，标记为异常注单，不进行部分派奖。
- 结算失败时记录错误并停止该注单的自动结算；重试由运营人员人工触发。
- 本期所有注单完成结算或被标记为异常注单后，期次状态变为已结算；异常注单视为本期结算完成，但必须保留人工处理记录。
- 结算应保存命中规则、命中奖级、排他性处理结果、计算明细、中奖积分和关联积分流水。

### 4.4 后台

- 品牌管理以配置为主，支持启用和暂停品牌。
- 品牌暂停时禁止创建新投注，保留登录、提现和已有订单处理能力。
- 品牌暂停不自动取消已有期次、注单、开奖或结算流程；相关业务继续按原规则执行。
- 品牌配置需要支持品牌域名、代理码和推荐码的管理，以及对应的启用状态和有效范围。
- 品牌配置需要支持代理层级、佣金规则和推荐奖励规则。
- 用户管理和身份审核。
- 品牌管理员只能管理所属品牌的用户、余额、订单、游戏配置和报表。
- 平台总管理员可以跨品牌查看用户、成员关系、状态和审计记录，但不能修改用户账户数据或踢人；平台总管理员对余额、订单、游戏配置和报表的管理权限仍按平台级权限执行。
- 后台权限采用“账号 → 角色 → 权限”的分离模型。
- 一个后台账号可以绑定多个角色。
- 一个角色可以配置多个权限。
- 当账号拥有多个角色时，最终权限取所有角色权限的并集，并自动去重。
- 权限需要支持平台级和品牌级范围；品牌级权限只能作用于账号被授权的品牌。
- 权限校验需要同时检查账号状态、角色绑定、权限类型和数据所属品牌。
- 游戏、奖级、赔率或奖金规则配置。
- 期次、订单、开奖和派奖管理。
- 注单需要支持正常、已结算、投注取消、判定取消和异常注单等状态或处理结果；注单状态需要记录对应期次状态、取消原因、异常原因、退款流水和结算处理结果。
- 异常注单需要记录异常原因、发现方式、处理人、处理时间、处理结果和相关积分流水。
- 风控、限额、异常订单和人工复核。
- 年龄、地区和身份验证第一期不做完整业务接入，先提供配置开关、统一接口和伪实现；是否启用及具体校验方式由品牌配置决定。
- 财务对账、报表和审计日志。
- 初始角色类型包括超级管理员、品牌管理员、运营、客服、财务、风控和审计；实际角色通过角色配置实现，不把权限硬编码到账号类型中。
- 角色和权限的创建、修改、绑定、解绑和删除需要记录审计日志。
