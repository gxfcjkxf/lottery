# 佣金更正历史通知与实际入账报表

0060将已经实际执行的佣金差额接入站内消息，并把补发、追回及更正笔数纳入现有佣金账本报表。两者均以真实非零资金目标和账本为依据，计划ready、批准、暂停、失败、零差额见证及当前钱包余额不能冒充入账。执行及管理规则分别见[23号执行合同](23-commission-correction-execution.md)和[24号管理合同](24-commission-correction-management.md)。

## 实际入账与事件原子性

`commission_correction_execution_targets`由pending转为applied且delta_points非零时，在同一金融事务写入唯一`commission.corrected` outbox事件及投递队列。钱包16桶、账本、目标审计、财务净额头、执行版本、事件和投递一起提交。事件写入失败或提交时缺少匹配事件，会回滚整笔步骤；任务可记为failed，只能运营显式技术重试，不能留下半笔资金或半个消息。

事件的aggregate_id和resource_id均为实际执行目标UUID，不是计划或整周期编号。私有outbox正文恰好为member_id、resource_id、points、ledger_entry_id、target_id五个字符串；points是规范非零有符号int64。数据库核对目标、执行批准、apply步骤、目标审计及完整佣金来源账本，拒绝金额或身份错位、额外字段、null、非规范数字及零额事件。插入还必须属于这个真实目标的创建事务，不能为历史目标补造事件。

每个实际目标只有一个事件。已提交事件不能改正文、品牌、类型、聚合编号或删除；只允许既有发布者修改published_at。零差额只有目标和财务版本，没有零额账本或消息。失效的旧任务、后续新结果和代理当前配置不撤回真实历史事件，也不让它变成新一笔收益。

## 站内消息与模板

既有in-app consumer验证私有事件见证，随后只向本品牌、本受益会员的收件箱写入公开正文：

~~~json
{"resource_id":"实际执行目标UUID","points":"-1"}
~~~

公开载荷不含ledger_entry_id、target_id、操作人员、原因、代理规则、财务版本或账户桶。正数表示过去的补发，负数表示过去的追回；这不是负佣金核算或负余额。原派发及人工修正消息仍保留。用户查询、已读和重试继续使用既有会话、品牌及本人限制，没有新增用户资金写入入口。

新增模板键与事件同名，全部模板现为20种。既有19种默认文案、修订和函数OID保留；每个既有品牌只新增一份默认更正模板及初始修订，新品牌正常初始化20种。更正消息即使模板版本1也必须带完整中英内容，不能用空快照回退到今天的文案。

模板在消息生成、收件箱落库时冻结。后来编辑模板不改旧消息或旧积分事实；消息消费也不改钱包、账本或净额头。前端额外显示固定历史说明，即使运营自定义模板也说明正数补发、负数追回、不代表当前余额、新收入或外部付款。默认内容及模板管理仍使用原有独立权限、版本及审计。

## 报表来源与精确汇总

现有`GET /api/v1/admin/reports/commission`与`.csv`保持路径、品牌选择、主库审计、查看/导出权限及筛选规则。报表独立选择原派发、人工修正和实际更正三类不可变账本后合并，避免多次修正把原入账重复展开。

更正只统计applied、非零目标绑定的真实`commission_correction`账本，身份、品牌、目标引用和delta必须一致。归属使用保存的代理、受益会员及cycle，不读取现在的比例；旧执行变stale后已入账部分仍统计。按实际`point_ledger_entries.created_at`半开时间窗口筛选，不替换为计划、任务、通知时间或投注时间。0059旧真实补偿账本也可以查询，无需生成旧消息。

totals现在恰好为十个精确十进制字符串：

| 字段 | 含义 |
| --- | --- |
| entry_count | 三类实际账本总笔数 |
| paid_entry_count | 原派发账本笔数 |
| paid_points | 原派发正额总计 |
| adjustment_entry_count | 人工修正账本笔数 |
| adjustment_credit_points | 人工修正增加总计 |
| adjustment_debit_points | 人工修正扣减绝对额总计 |
| correction_entry_count | 实际更正账本笔数 |
| correction_credit_points | 更正补发总计 |
| correction_debit_points | 更正追回绝对额总计 |
| net_points | 三类账本的有符号净变动 |

entry_count等于三项笔数之和。net_points等于paid_points＋adjustment_credit_points－adjustment_debit_points＋correction_credit_points－correction_debit_points。前九项非负，只有净额可负；所有汇总可以超过int64，SQL使用numeric，Go与客户端用任意精度整数，不能经JavaScript Number。补发和追回可以同时非零，净额0不表示没有资金变化。

原入账1、更正追回1的完整窗口为2笔、paid_points=1、correction_debit_points=1、net_points=0。只包含后续追回的窗口则为1笔、net_points=-1；原信用发生在窗口之外，不表示钱包透支。零差额财务版本、冻结/解冻及普通钱包调整不进入本报表。

## CSV版本与部署

佣金CSV升级为`X-Report-Format-Version: 2`，审计也记录版本2。列顺序为原十二个元数据列，接上述十个totals字段，合计22列；新增三项位于net_points之前。其他报表格式仍为1。服务和SDK核验全部分组之和、规范金额、计数及净额等式；保持10000组/4MiB上限、UTF8 BOM、负净额安全前缀、SHA256、字节数、完整筛选导出及独立审计。客户端拒绝版本1套用新版布局。

正常migrate至0060后协调部署API、worker及前端。不得修改旧迁移校验和、跳过新字段或用旧SDK接受不完整金额；旧佣金导出审计仍保留版本1，不改写。迁移新增模板、事件守卫及报表部分索引，不改旧账本、积分、批准或更正金融开关，也不扫描旧目标补造消息。六个新增或替换函数固定pg_catalog、应用schema、pg_temp查找路径；大库索引及迁移锁等待须安排窗口，不宣称零停机。

## 验收与剩余范围

实际业务测试覆盖补发、追回、零见证、旧任务失效后历史保留、通知故障/缺事件的资金回滚、显式恢复及唯一入账。0059真实已执行目标升级后逐表金融指纹不变、旧事件零回填，历史补造被拒绝；已有文案/OID、初始修订、新品牌及重复迁移另有升级测试。

双端真实浏览器沿正常投注、结算、更正、新批准、原键未知恢复和暂停继续形成一积分追回，验证报告的原入账与补偿分项、22列完整CSV及摘要、用户本人消息、重复消费去重、模板改后旧快照不变、中英历史说明及金融指纹不变。浏览器专项不替代真机、生产容量或客户人工代码审核。

OPEN-117原人工修正后再次更正的特殊净额组合仍整期blocked及null差额，不提供绕过。按投注归属的跨彩种佣金分析、不可变日月归档、外部通知/支付和完整生产验收仍未由本报表实现，不能把实际入账报表当作有效应付、当前余额或封存财务账。
