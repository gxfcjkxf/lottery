# 佣金最终注单事实与计佣基数

本模块提供真实结算事实、已确认的基数、同一基数的精确差额计算和可配置周/月日历核心，不创建佣金记录或派发积分。已确认采用差额分配、独立佣金积分、不按每个彩票期次生成待结佣金；周期边界及人工/系统派发由品牌配置。现有代理管理开关不启用佣金财务流程，完整周期批处理、审核、派发及更正后的佣金回溯仍需实现。

## 内部调用

`backend/internal/commission.Source.FinalOrderTx(ctx, tx, brandID, orderID)` 必须使用调用者事务及可信品牌、注单编号，不提供公共 HTTP 接口。未来的后台接口仍须独立校验会话、品牌权限和请求幂等，不能把传入品牌编号当作授权。

返回 `Resolution`，正常排除时 `Fact=nil`，并给出原因：

- `cancelled`：投注取消或判定取消。
- `abnormal`：异常注单，不计佣。
- `correction_open`：本期正在冲正或重新结算，旧结果和部分新结果均不计入。
- `not_final`：尚未形成整期最终结算。
- `final`：返回当前最终结算代次的 `OrderFact`。

参数非法返回 `ErrInvalid`；未知注单和跨品牌读取统一返回 `ErrNotFound`；期次被修改时返回 `ErrBusy`，调用者须回滚后重试；本应最终有效但证据缺失或不一致时返回 `ErrEvidence`，不能把错误降级为零额佣金或静默跳过。

## 最终事实证据

读取先取得该期次的共享锁并采用 `NOWAIT`，直到调用者结束事务。它阻止已读取的当前开奖结果、结算任务和代次被更正替换；不会在调用者持有钱包时等待期次，从而避免与结算的“期次到钱包”锁顺序冲突。结果仅在该事务内稳定，提交后不得把缓存事实当作未来入账授权。

有效事实同时要求：

- 注单为 `won/lost`，没有退款，期次已结算，且没有未完成的结果更正。
- 期次指向当前已完成的任务；计算记录的品牌、任务、期次、注单、购买版本、定义摘要、开奖摘要和中奖结果均匹配。
- 本注单的结算目标为 `paid`，计算编号和派奖编号与注单一致。零奖金须无派奖流水。
- 原投注借记账本匹配品牌、会员、账户、注单和业务类型。来源分配合计等于投注额，分配、十二桶变化和前后余额逐项一致。
- 正额奖金具有本计算对应的中奖积分入账；业务引用、操作键、来源分配、十二桶变化和前后余额均匹配。

`OrderFact` 保留品牌、会员、账户、彩种、期次、玩法版本、投注借记序号、当前任务和计算编号、结算代次、投注/结算时间及原来源分配。原 `attribution_snapshot` 原样保留在内部字段，JSON 序列化不输出它。不得用今天的代理树或比例补造旧注单归属；快照中的旧版、空佣金政策不代表存在可派发的财务规则。

## 已确认的基数

`Bases(status, stake, prize)` 只接受经过最终证据校验的 `won/lost`：

- 流水基数为有效投注额，包含充值、中奖和赠送三种支付来源。
- 输赢基数仅对 `lost` 使用有效投注额；中奖注单和平局不计入。即使中奖额低于投注额，也不擅自改为按净亏损计佣。
- `lost` 必须奖金为零；负数、零投注额、其他状态和不一致结果均拒绝。

单注积分沿用精确 `int64`，JSON 基数采用十进制字符串，可正确传输超过 JavaScript 安全整数范围的值。实际入账仍只允许整数；内部差额计算保留精确分数，不提前舍入或代表已入账金额。

## 同一基数的精确差额计算

`DifferentialSameBasis(base, ratios)` 接受共同基数及从上级到下级的比例路径，沿用代理模块0至1、最多六位小数的规范字符串，拒绝下级超上级、负基数、空路径或超过32级。每层使用自身与下一层的比例差，末层使用自身比例；返回规范的十进制分子/分母字符串。

基数100、比例10%/6%时结果为4/6；三层10%/6%/2%为4/4/2。各层精确结果合计等于最高层比例乘基数。函数不选择混合计佣模式、不舍入、不汇总周期，也不读取今天的代理树代替购买时快照；不同基数路径仍待OPEN-113确认，不能强行套用同一基数函数。

## 可配置周月日历核心

`Calendar.WindowAt(t)` 接受显式时区、周期类型和本地边界时刻，返回包含该时刻的UTC半开区间 `[From, To)`；边界上的时刻归新周期。它不决定传入的是投注时间还是最终结算时间，此项仍待OPEN-114确认。

- `Timezone`：有效时区名称或UTC，不使用机器的Local时区。
- `Cycle`：weekly或monthly；`BoundaryTime`为严格HH:mm:ss。
- 周周期须提供`Weekday`，0为周日、6为周六；月字段须未设置。
- 月周期须提供1至31的`MonthDay`及显式`ShortMonth`，周字段须未设置。短月不足指定日时，可配置last_day取月末，或skip略过该月边界；skip形成的区间可能跨两个月，不是漏记该区间内业务。
- 不用固定168小时或30天计算边界。夏令时导致本地边界不存在或对应两个时刻时返回`ErrCalendarBoundary`，不静默选偏移、重复结算或提前派发。

这里是内部计算配置，不是已实现的品牌配置API或调度任务。彩票期次仍按原投注/派奖/退款流程关闭，不等待周/月佣金周期，佣金批处理也不改变下一期开放规则。

## 完整佣金模块仍需完成

`OPEN-110`的差额分配和新增佣金积分已经确认；`OPEN-004`已确认按周期批处理、不按彩票期次生成待结佣金，边界和人工/系统派发可配置。新增来源的投注/提现规则、混合计佣模式的差额及注单归属时间分别记录在OPEN-112至114，本模块不替用户选择。

后续必须保存购买时的完整财务规则，建立不可改写的计提、周期、审核、调整和派发记录，以品牌、注单、计算代次和代理身份绑定幂等证明；结果更正要先冲正原佣金影响，再使用新代次计算。本次读取只排除未完成更正并跟随最终代次，不能替代已派发佣金的追回或补偿。

## 开发验证

纯计算测试覆盖有效输钱、中奖、平局、低于投注额的中奖、非法状态/金额及超过安全整数和 `int64` 最大值边界；差额覆盖两层/三层、等比、分数及合计不增额，日历覆盖闰年、短月、UTC交界、夏令时167/169小时及异常边界。四时区全年取样验证区间包含输入时刻、相邻区间无重复或空隙。真实 PostgreSQL 隔离测试通过实际投注、取消、判定取消、异常标记、派奖和结果更正验证最终事实；本次数学/日历新增部分不写数据库。

测试同时核对业务状态、余额、完整账本、任务、审计和事件不被读取修改；验证期次忙、共享锁阻止并发更正、第一代中奖更正为第二代输钱，以及计算、目标、投注借记和派奖流水损坏时的拒绝。故障注入仅在独立测试 schema 的回滚事务内执行，不关闭正式业务守卫。

本阶段没有新增业务表、权限、公开接口或 UI，平台 worker 尚未调用该模块；生产容量和实际佣金财务闭环不在这些测试结论内。
