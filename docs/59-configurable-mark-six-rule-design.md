# 六合彩玩法配置表达与通用规则结构设计

设计日期：2026-10-19；当前状态核对：2026-10-20。A/B/C阶段已接入通用结构、编辑器、验证审核发布、配置式销售/投注/结算及JSON/HTML/JS渲染DOM来源，见第13至15节。第1至12节为设计时盘点和阶段边界，不能当作当前待实现清单；旧组件及导入清理见第15.11节，六合彩和加拿大新销售统一见第15.13节，旧开奖清理见第15.15节。

本设计将现有全部六合彩玩法表达为可复用规则组件的组合，并让同一份玩法定义驱动编辑器、用户选号、计注、报价、判奖和结算。目标是在组件能力范围内，新增玩法只需创建配置和完成验证审核，不再新增玩法枚举、前端分支、赔率字段或专用判奖函数。

## 1 设计依据与边界

原始要求见 [规则引擎规格](03-rule-engine.md)、[需求讨论中的通用玩法引擎](requirements-draft.md#411-通用玩法引擎方向)。现有通用引擎已经具备号码模型、选号展开、属性条件、条件树、奖级、精确金额、模拟和规则版本工作流；设计之初共享六合彩投注及结算通过专用目录和函数执行；现已接通配置式链路，专用协议历史订单仍按原快照处理。

最初设计盘点覆盖当时仓库的全部六合彩玩法；当前通用配置也用于加拿大及自定义模型，见第15.7节。参考站有而仓库没有的玩法，只记录其配置扩展方式，不视为已经批准新增。加拿大玩法和其他彩种不在本阶段逐项盘点，但新组件不以六合彩业务名命名。

以下口径继续作为配置转换基线：

- [58号文档](58-mobile-mark-six-continuous-selection.md)已经确认的49处理、正肖计次、过关、组合固定赔率和A/B盘口语义。
- 每个生肖对应实际属性版本中的号码集合，不能写死为4个号码；49个号码分配至12个生肖时存在5号码生肖。属性不按当前年份在代码中推算。
- A/B盘仅区分价格，共用选号和判奖定义。当前不增加参考站另名的“特码A/B”“正码特B”变体。
- 组合按具体玩法固定价格，保留现有独立奖级及含0尾价格。不得因参考站成员价格不同而改用最低价或最高价。
- 普通复式、不支持胆拖；一个混合批次展开后合计最多1000注，超限拒绝，不截断。
- 不引入脚本、插件运行器、任意函数或任意计算公式字符串。基础运算组件需要代码实现，组件已能表达的新增业务玩法通过配置实现。

## 4 统一表达约定

本节的符号仅用于阅读表达表，不是可执行公式字符串。

| 符号 | 定义 |
| --- | --- |
| T、R、A、Pp | 特码单球、六个正码、全部七球、原始开奖顺序中的第p个正码；位置显示1至6，序列索引在协议中统一明确换算 |
| U | 一条已展开注单选择的选项集合，不是玩家尚未展开的候选池 |
| Z(n)、W(n)、E(n) | 号码在本期快照中的生肖、波色、五行 |
| H(scope,U) | 结果范围内属于所选选项号码并集的开奖位置数；一个位置只计一次 |
| C(scope,U) | 至少有一个号码命中的所选选项个数；一个选项只计一次 |
| D(scope,属性) | 结果映射为该属性后的不同属性值个数 |
| S、O、N | 当前单线投注积分、购买时固定的含本金赔率、实际命中次数 |

H和C必须分别存在。例如两个生肖中一个出现三球、另一个没有出现时，H为3而C为1；二连肖要求C等于2，不能用H至少2替代。选项号码集发生重叠时，同一球可覆盖多个选项，但H仍只计一个位置；定义可以配置选项映射是否允许重叠，不能默认各属性必然互斥。

“属性”可以用明确号码集、号码到标签的映射，或白名单数值转换产生。对生肖/波色/五行采用版本映射，对尾数采用模10，对头数采用整数除10；两种表示经解析后使用一致的选项匹配接口。

| 半波 `half_{颜色}_{big/small/odd/even}`，12项 | 特码波色匹配且所选大小或单双匹配 | T=49先push；每项1注，只派一次 | R3/R4；C1/C2/C5/C6/C8/C9 |
| 半半波 `quarter_{颜色}_{4种组合两面}`，12项 | 特码波色、大小、单双同时匹配 | T=49先push；每项1注 | 同上 |
| 七色波 `seven_red/blue/green` | 对A按波色分组累计权重，R每球2、T每球3；所选色为唯一最高分 | 最高分并列时颜色项push；49按绿波参与权重；2/3与1/1.5等价 | R7；C1/C2/C3/C5/C6/C8/C9 |
| 七色波和局 `seven_tie` | 上述计分结果中最高分颜色数>1 | 是则中奖，否则未中；这是一种中奖选项，不是push动作 | 同上 |
| 总和 `total_big/small/odd/even`，4项 | sum(A)≥175 / ≤174；sum(A)模2为1 / 0 | 49计入和值，无49退本 | R4/R5；C2/C3/C6/C8/C9 |
| 总肖 `zodiac_count_{1..7}`，7项 | D(A,Z)等于所选数量 | 49生肖参与去重；同生肖多球只算一个；每项一次派彩 | R7；C1/C2/C3/C6/C8/C9 |
| 总肖单双 `zodiac_count_odd/even` | D(A,Z)模2为1 / 0 | 同上 | 同上 |
| 家野 `domestic/wild` | Z(T)属于家肖集合 / 野肖集合 | T=49先push；每项1注 | R3/R4/R7；C1/C2/C5/C6/C8/C9 |
| 天地 `heaven/earth` | Z(T)属于天肖集合 / 地肖集合 | 同上 | 同上 |
| 前后 `front/back` | Z(T)属于前肖集合 / 后肖集合 | 同上 | 同上 |

生肖分类表保存明确成员，不依赖生肖数组中的位置推算：家=牛马羊鸡狗猪；野=鼠虎兔龙蛇猴；天=牛兔龙马猴猪；地=鼠虎蛇羊鸡狗；前=鼠牛虎兔龙蛇；后=马羊猴鸡狗猪。分类映射到号码时仍读取本期生肖快照。

### 5.5 正码过关

`parlay` 每注选择2至6个不同正码位置，每位置只允许选择第5.1节的17种位置属性之一；实际所选关组成一注，不展开为各关数的所有子组合。

| 环节 | 配置表达 |
| --- | --- |
| 选号 | 选择结构化的 `{position, option_id}`，不再用位置乘100加属性下标作为通用协议 |
| 各关判定 | 引用已发布的位置属性规则及其确定版本；各关按Pp判定won/lost/push |
| 组合判定 | 任一关lost则整注lost；有效关全部won时整注won，push关价格因子为1 |
| 购买取价 | A/B盘分别解析并保存每关价格及规则引用；展示全关价格乘积，不创建过关固定价 |
| 结算派彩 | S乘以非push关购买赔率之积，精确计算后对该单线舍入一次 |
| 组件 | 复用R5/R7/R8，补C2/C3/C5/C6/C7/C8/C9 |

当前已确认口径不引入“全部关因49和局”的额外业务规则。后续第12节要求核对开奖跨组去重的一致性；不能在转换中用另一个假设修改历史结果。

## 6 49处理总表及计注不变量

| 条件作用范围 | 开出49时 |
| --- | --- |
| 特码号码、正码号码、位置号码 | 正常号码匹配 |
| 特肖、五行、平特一肖、连肖、生肖不中、正肖、总肖 | 使用49的本期属性；正肖仅当49在正码中计次 |

| 头尾、连尾、尾不中、自选号码不中、连码、总和、七色波 | 按各自条件正常参与，无统一49退本 |

配置不得对所有属性玩法统一设置49退本。push必须保存为独立结果并按原扣款来源退本，不作为赔率1的中奖；普通中奖返还包含本金，中奖派彩和退本分开记账。当前所有非push的有效投注口径保持原有业务定义。

## 8 通用规则结构提案

### 8.1 对象边界

以下是完整方案的对象边界，字段名用于讨论，不是已经上线的HTTP API。A阶段实际Go结构及其schema-v2入口见第13节，不在旧schema-v1上隐式推断模式。

| 对象 | 主要字段 | 版本和归属 |
| --- | --- | --- |
| GameModel | 号码池、开奖组、数量、顺序、组内/跨组重复约束 | 彩种级；已有玩法和期次使用时不可原地改写 |
| AttributeSet | 属性组、选项、号码或标签映射、完整性/分区约束、生效区间 | 彩种级不可变版本；期次固定实际适用版本 |
| PlayDefinition | schema/语义版本、模型引用、选项域、选号、指标、push、奖级、派彩、价格规格、限额、展示 | 玩法级不可变发布版本，归属平台或品牌 |
| PriceBook | 定义版本、盘口、选项/价格类别/奖级键及精确价格 | 平台价格及品牌销售价格各自版本；品牌不得超平台对应单元 |
| SalesPolicy | 启停、开放玩法、单注/单期/会员限额及价格表引用 | 品牌/彩种或玩法范围，沿用既有服务层准入 |
| PurchaseSnapshot | 规则hash与内容、属性解析快照、价格版本及采用价格、展开线、积分与来源分配 | 购买时固定；结算只读 |

规则定义声明“从哪里绑定属性”，期次提供实际属性版本。解析后的执行定义连同实际映射保存到购买快照并计算hash；不能仅保存 `latest` 引用。规则内容hash和解析后执行快照hash分别用于审核与订单复核，不混为一个含义。

价格可独立调节，但价格规格由规则定义声明；价格变化走明确版本及现有发布授权，定义条件变化走规则验证审核。价格发布仍校验定义版本、价格完整性、金额范围及权限。不是把修改价格变成修改判奖公式。

### 8.2 玩法定义的逻辑字段

```text
PlayDefinition
  schema_version              明确的新协议版本
  semantics_version           解释语义版本
  identity                    稳定ID、归属、代码和双语名称
  model_ref                   所属彩种模型及其版本
  attribute_bindings          所用属性组和期次版本绑定方式
  option_domains              号码、明确集合、属性、数值选项、关引用
  selection                   选项组、每注数量、候选上限、重复/位置约束
  expansion                   singles / combinations / as_selected
  stake                       固定单注乘倍率或玩家逐项/每组合积分的明确模式
  metrics                     有类型的结果统计节点
  push_when                   可选的独立和局条件
  prize_tiers                 奖级ID、条件、价格引用、派彩模式、排他性和封顶
  tier_policy                 沿用已明确的排他/累加选择策略
  pricing_spec                价格维度、组合类别和允许盘口
  rounding                    half_up及line/tier/order范围
  limits                      组合、倍率及投注预算
  presentation                分组、控件、顺序、双语名称/说明
```

对象没有相应能力时省略可选字段；必需字段、类型、引用和策略缺失则拒绝发布。price、scope、49处理和组合模式不得通过代码名称、页面标题或默认成功结果推断。

单线投注S为展开后的该线整数积分，来源于玩家输入与服务端规则；如果使用通用固定单注/倍率流程，则由unit_points×multiplier计算。当前六合彩任意逐项积分的能力要通过显式stake模式保留，不能强制转换为固定unit_points而改变金额。

### 8.3 节点类型与计算顺序

| 类型 | 允许的操作及参数 | 输出 |
| --- | --- | --- |
| ResultScope | `all/regular/special`、声明位置集合 | 保留来源与位置的有序号码序列 |
| Mapping | identity、明确集合、属性查表、已定义标签分组 | 选项对应号码集或号码对应标签 |
| NumberTransform | 模、整数除、数位和，参数为校验后的正整数 | 数值或数值序列 |
| Aggregate | sum、count、distinct_count、match_count、covered_option_count、weighted_group_sum | 整数或精确数；分组统计为标签到精确数的映射 |
| Compare | equals、in、between，以及有类型的数值比较 | 布尔值 |
| Logic | all、any、not | 布尔值 |
| GroupResult | 指定标签是否唯一最高、最高分并列个数 | 布尔值或整数 |
| Payout | fixed_return、net_profit_per_hit、product_of_legs | 精确返还金额与解释明细 |

指标只引用输入、已声明的选择组或在前面定义的指标；禁止循环引用、递归规则调用、网络读取和数据库查询。属性查表使用输入快照。过关仅引用明确版本的普通单关规则，不允许过关嵌套过关。先复用现有条件深度/节点/解释预算，再将新指标及各关成本纳入同一预算；不无依据提高上限。

节点签名必须区分号码序列、标签序列、选项集合、数值、分组分值和布尔值。集合成员检查、数值比较及与所选统计选项的比较使用明确参数；标签不能隐式转数字，序列不能隐式取首项。单球数值仅从明确只含一个位置的scope读取，缺值或类型不匹配拒绝。

执行顺序为：校验定义和绑定 → 规范化选择 → 按选项而非覆盖号码展开 → 逐线解析价格并核对预算 → 下单保存快照 → 开奖后计算指标 → 判push → 判奖级 → 精确计算与舍入 → 输出结果 → 服务层原子记账。

配置语义例外只出现在配置中：例如转换后的六合彩属性集声明49为绿；引擎本身不知道“49”“生肖”“马年”或“七色波”的含义。

### 8.4 价格规格

一期覆盖现有六合彩所需的四种价格结构：

1. 选项价：按选项和盘口取价，例如特码07、马生肖、某位置绿波。
2. 固定玩法/档位价：按玩法和盘口取价，例如二连肖、五不中，不读取组合成员价格。
3. 多奖级价：购买时固定每个潜在奖级价格，开奖后仅选择对应奖级，例如三中二及二中特。
4. 明确组合类别价：按展开线的选项判断互斥类别，例如包含0尾与不包含0尾，两类都必须明确有价格。

过关使用各关购买价格的乘积；这是C7的派彩组合方式，不是第五套静态过关价格表。价格键使用稳定选项ID、类别ID和奖级ID，不在协议中解析字符串后缀 `_zero` 或 `_full`。

价格分类只能依赖购买时已知的选择和绑定属性，不依赖未知开奖结果。多奖级在购买时保存所有潜在价格；开奖只能选择已存奖级，不能临时查当前价。缺价、类别重叠、未知选项或过期定义均明确拒绝。完整性按“所启用玩法全部可达价格单元”检查，不继续要求所有彩种永久填满统一669键。

参考站的逐生肖连肖价、逐号码不中价可以作为未来价格规格扩展需求，但一期不实现最低/最高成员价策略。没有业务选择规则时，不把多个成员价格自动合成为一个组合价。固定组合价与选项价的差别在编辑器中明确显示。

### 8.5 派彩与结果输出

| 模式 | 精确计算 | 适用范围 |
| --- | --- | --- |
| fixed_return | 命中时S×O，未中0 | 普通单项及组合 |
| net_profit_per_hit | N>0时S×[1+(O−1)×N]，N=0时0 | 当前正肖；本金仅一次，命中数不在代码设4次封顶 |
| product_of_legs | 任一关lost为0；其余按S×有效关O之积，push关因子1 | 当前正码过关 |
| push动作 | 原来源退还S，不进入中奖派彩 | 独立于上述模式 |

当前六合彩转换配置明确 `rounding=half_up`、`rounding_scope=line`。先精确计算一条展开线的全部返还，再舍入一次；正肖不能逐次命中舍入，过关不能逐关舍入。通用引擎保留已有其他舍入范围，不能将它们全局改为line。

统一输出至少包含：规范选择、展开线标识、won/lost/push、命中奖级、统计值、采用价格/各关价格、原始精确金额、最终整数派彩、退本金额及有效投注。模拟输出增加上述字段；布尔won不能单独区分push。规则返回计算事实，具体奖/退款账本由现有服务层执行。

## 9 配置样例

以下为设计用的简写YAML片段，不是schema-v1请求，也不是可直接发布的完整Definition。共同的模型、版本、双语展示、预算、价格表及权限引用按第8节补齐。

### 9.1 特码和特肖复用同一匹配组件

```yaml
# 特码
domain: {kind: numbers, values: [1, 2, 3, 4, 5, 6, 7]} # 示例池，完整模板为1至49
selection: {per_line: 1, expansion: singles}
match: {scope: special, metric: match_count, counting: occurrences, equals: 1}
payout: {kind: fixed_return, price_dimensions: [option_id, plate]}

# 特肖：只替换选项域及其映射，仍为每选项一注
domain: {kind: attribute_options, binding: period.zodiac}
selection: {per_line: 1, expansion: singles}
match: {scope: special, metric: match_count, counting: occurrences, equals: 1}
payout: {kind: fixed_return, price_dimensions: [option_id, plate]}
```

选择生肖时，服务端从期次字典解析该选项的全部号码；注单仍保存选项身份，不能只存号码并集而丢失“买了哪个生肖”和对应价格。

### 9.2 二连肖与合肖复用选项域并使用不同条件

```yaml
domain: {kind: attribute_options, binding: period.zodiac}
selection: {per_line: 2, candidate_max: 12, expansion: combinations}
# 二连肖
match: {scope: all, metric: covered_option_count, equals: 2}
payout: {kind: fixed_return, price_dimensions: [plate]}
# 二肖中：换scope、命中数，并声明push；不新增解释器类型
# match: {scope: special, metric: covered_option_count, equals: 1}
# push_when: {scope: special, metric: raw_value, equals: 49}
```

### 9.3 三中二和含0尾价格

```yaml
# 三中二
selection: {domain: numbers, per_line: 3, expansion: combinations}
metrics:
  - {id: regular_hits, scope: regular, op: match_count, counting: distinct_numbers}
tiers:
  - {id: hit_two, when: {metric: regular_hits, equals: 2}, price_slot: hit_two}
  - {id: hit_three, when: {metric: regular_hits, equals: 3}, price_slot: hit_three}
payout: {kind: fixed_return}

# 二连尾价格类别：按每条展开线分类，不是按整批候选池分类
price_categories:
  - {id: includes_zero, when: {selected_option_contains: tail_0}}
  - {id: excludes_zero, when: {not: {selected_option_contains: tail_0}}}
```

### 9.4 总肖和七色波使用派生统计

```yaml
# 总肖
metrics:
  - {id: signs, scope: all, op: map_attribute, binding: period.zodiac}
  - {id: sign_count, input: signs, op: distinct_count}
win_when: {metric: sign_count, equals_selected: count_option}

# 七色波颜色项
metrics:
  - id: scores
    scope: all
    op: weighted_group_sum
    group_by: {attribute: period.wave}
    weights: {regular: "2", special: "3"}
  - {id: top_count, input: scores, op: max_tie_count}
push_when: {metric: top_count, greater_than: 1}
win_when: {input: scores, op: selected_group_is_unique_max}
```

### 9.5 无代码新增自定义号码组

## 10 编辑器与运行链路

### 10.1 编辑和展示

提取现有完整编辑器为共享能力，平台和品牌按资源归属使用；平台简化表单保留为快捷创建方式，生成同一份定义，不承载另一套语义。模板可以预填范围、号码组、判奖和价格规格，但保存后以定义为唯一解释来源。

编辑步骤：选模型和模板 → 配置选项域与映射 → 配置每注/复式规则 → 选择结果范围及条件 → 设置push与派彩 → 配置价格规格和两盘价格 → 设置限额及展示 → 输入独立预期案例 → 查看模拟 → 保存验证和审核。

同页提供用户选号预览和逐节点模拟说明。号码网格、属性选项、统计选项、位置选项、组合选择、过关选择为可复用控件类型；控件由定义声明，不能通过玩法代码选组件。用户点击多个独立选项与加入组合批次仍保持现有操作流程。

内置控件、错误与动作文案使用三端现有中英文catalog。运营新增的玩法名称、选项名称、说明保存双语本地化内容，经同一i18n读取；发布前检查当前支持语言完整，不能每新增玩法都要求修改前端静态翻译目录。说明由配置摘要和双语内容共同生成，不能在用户端重新写一套判奖规则。

界面复用 [48号设计规范](48-ui-architecture-and-design-system.md)，不小于11px，保留设备预设并覆盖安卓/iOS横竖屏、短视口及320 CSS px重排。

### 10.2 共享彩种与品牌销售

平台共享彩种及期次仍为一个来源，品牌接入不复制开奖。平台定义的玩法不能被品牌直接改写；品牌仅调整被授予的销售、价格和限额。品牌自有规则沿用品牌范围的编辑审核流程，平台查看权限不转换为品牌写权限。

共享平台玩法目前缺少与品牌rulebook相同的完整发布流程。C9需要接通“所属资源内草稿、验证、审核、激活”，具体平台审核角色和价格发布流程在详细设计中确认，不沿用品牌接口绕过授权。既有允许自审的业务口径不自动改为双人审核。

报价返回定义、销售、价格及属性绑定版本，用户确认基于这些版本。正式提交重新校验版本、身份、封盘、品牌准入、完整价格、限额和余额；变化则明确要求重新核对。禁止客户端上传最终赔率作为可信价格。

### 10.3 快照与历史

新单保存明确的定义和解释语义版本、解析属性、所有潜在奖级价及各关版本、原始/规范选择、展开线、实际金额和来源分配。结算按绑定快照计算；调整模板、号码映射、选项顺序、当前价格或玩法名称不能改写旧单含义。

当前在正式发布前使用单一基线安装，发布后冻结迁移并追加增量，见[安装约定](../README.md#空库安装)。本设计不提出旧开发库增量升级、历史补写、新旧输入兼容或失败回退流程；不运行数据库操作，也不授权清空已有开发库。后续实现以新基线及独立试用数据验证配置链路。正常历史及已结算结果仍保留，不能重算覆盖；如果未来确需处理旧执行语义下的未结订单，须单独盘点并明确处置后再切换，不在本阶段承诺兼容执行器。

### 13.2 实际结构与调用方式

`ConfiguredCatalog` 固定 `schema_version=2`、`semantics_version=1`，显式声明模型、跨组去重开关、价格上下界、可用盘口、属性组、选项域及玩法。每个玩法保存选号、积分模式、结果条件、价格、派彩及舍入策略。条件和统计使用内嵌的类型化表达式树，不增加任意脚本或指标引用语言。

映射支持明确号码集、属性标签、映射交集和数值转换；选择支持逐项拆注、K项组合和原样成注。集合匹配显式区分出现次数、不同号码数及命中选项数。统计支持按原始位置取值、和值、模、整数除、数位和、不同属性值数量、精确加权分组及最高分并列判断。

A阶段只接收调用方已确定的 `ConfiguredBindings` 和 `ConfiguredPrices`。前者包含实际属性版本及标签号码字典，后者包含价格版本和显式盘口价格表；没有默认年度、当前价查询、空价格补全或跨实现回退。`CheckPriceCeilings` 提供品牌价格不得超过平台对应价格单元的纯计算检查，服务层接入仍属C阶段。

Go调用示意，`bindings`、`prices`、`draw` 由调用方显式提供：

```go
catalog, err := rules.MarkSixConfiguredCatalog()
// 检查err后创建不可变计算快照。
engine, err := rules.NewConfiguredEngine(catalog, bindings, prices)
// 检查err后逐项/逐组合报价；这里购买一个特码选项。
quote, err := engine.Prepare(ctx, []rules.ConfiguredRequest{{
    PlayID: "special_numbers", Options: []string{"7"},
    Plate: "A", Points: 10, Multiplier: 1,
}})
// 检查err后才可以使用quote；本阶段不执行实际扣款。
result, err := engine.Settle(ctx, quote, draw)
```

上述片段只说明调用顺序，不是绕过错误处理的业务代码。`Prepare` 无开奖输入，不预先判断中奖；它拒绝重复选择、重复批次线、错误盘口、缺价、价格类别无匹配/多匹配、过多组合及金额溢出。多奖级保存各潜在价格，过关保存结构化关引用及各关价格；保留当前每项积分，并另支持显式固定单注乘倍率模式。

`Snapshot()` 返回目录、属性和价格的深拷贝序列化内容；`RestoreConfiguredEngine` 严格恢复该内容。`DefinitionHash()` 只标识规则目录，`SnapshotHash()` 同时绑定实际属性及价格。调用方修改原结构或返回字节不会改变已创建的计算器。结算要求快照hash一致，并重新推导报价，拒绝调用方篡改金额、选项、奖级价或关信息。

`Settle` 输出各线won/lost/push、命中奖级、精确金额、整数派彩、退本及有效投注，并保留条件Trace和各关结果。当前全部六合彩定义使用line舍入。通用order舍入和玩法总封顶按同一报价中的玩法ID及盘口分别汇总；`Rounding` 输出权威汇总及封顶明细，各线金额仅作为独立舍入展示。原通用引擎的tier、line、order与混合奖级策略均有对照用例。

### 13.3 目录与行为验证

### 13.4 当前边界

A阶段结束时，C1至C7的纯计算路径和全部六合彩配置已经落地，C8和C9尚未接入。后续B阶段的编辑器及预览接口见第14节；发布审核及实际销售绑定仍留在C阶段。

新模板显式设置 `disjoint_draw_groups=false`，保持现有X_PLUS_Y跨组检查行为供一致性对照；组件已支持声明为true并拒绝跨组重复。业务模板是否启用该约束仍按第12节单独确认。总肖1价格和规则表达保留，A阶段不自动删项或改变判奖；发布时的属性相关可达性分析仍需后续审核集成。价格分类在实际购买选择上严格检查唯一匹配，不宣称当前纯结构校验已经证明所有组合分类静态完备。

过关只引用同一冻结目录中的普通单关定义，不支持嵌套过关。对当前不可能出现的全关push不生成默认成功结果。若未来其他模型需要此场景，应先明确业务语义再扩展组件。

## 14 B阶段配置编辑、动态选号和模拟

### 14.1 可操作入口及边界

本节记录B阶段的内存试验区；当前持久化草稿、审核发布及真实销售已在第15节接入。总后台和品牌后台的共享彩种页面内增加“可配置规则试验区”；品牌后台原有规则版本页面也使用同一组件。先载入六合彩演示配置或导入草稿文件，再编辑、验证、选号、计算和模拟。该区编辑的是内存草稿，离开页面前应导出JSON文件；没有数据库草稿、自动保存、规则版本创建、审核、激活或发布动作。

B阶段曾提供用户端草稿文件预览工具；该临时入口及组件现已移除，普通用户端只使用正式发布的彩种销售页面。草稿编辑、验证、导入导出及模拟仍位于后台规则工作台，不在用户端暴露开发工具。

后台和用户端共同使用 `ConfiguredSelection.vue`，不根据玩法ID、名称或 `source_code` 选择组件。它按 `selection` 控制逐项/组合/原样成注、可选数量、过关不同位置限制，并按 `stake_mode` 显示每注积分或配置单注乘倍数。覆盖四/五个号码的属性选项仍保留一个选项身份。号码映射只负责展示；权威计注、取价、判奖和派彩仍调用A阶段引擎，不在浏览器重写判奖逻辑。

候选奖级赔率列出某选项可能涉及的价格，不将价格分类或多奖级误显示成已确定赔率；过关选项显示其单关候选价格。后台“计算注数”输出实际展开线和冻结的各奖级/各关价格，模拟输出中奖、未中、退本、原始精确金额、整数派彩、有效投注、舍入汇总及条件Trace。金额始终按十进制字符串传输。

### 14.2 新增玩法操作

最直接的新增流程是展开“新建号码组玩法”，填写新标识、完整中英文名称、覆盖号码、结果范围、位置、退本号码以及每个声明盘口的赔率。位置输入从1起，生成规则时转换为原始开奖顺序的零基索引；留空表示整个所选范围。单个开奖值范围才支持这个快捷表单的指定号码退本；多球范围不明确对应值时直接报错。

例如填写覆盖号码 `2,7,19,31`、正码范围、位置3、49退本、A盘2.5、B盘3.5，生成一个组一个选项、每选项一注的普通schema-v2定义。它只组合号码映射、`match_count`、`raw_value`、条件及选项价格，不新增运行时类型或业务分支。少填任一盘口价格会报错，不用演示价格补全。

其他玩法可从已有定义复制，再通过树形字段编辑器修改选号规则、映射、条件、价格分类、奖级、派彩、属性绑定和价格。复制生成独立选项域并删除原来源对账标记；显式价格引用仍保持原配置，需要独立定价时应调整对应价格键和价格表。各节点支持修改基础值、复制/删除列表项；可选字段、全新树结构和字典键也可在完整配置JSON中编辑后“应用配置”。JSON只承载既有声明式组件，不执行脚本。折叠的子组件按展开渲染，避免整个价格和属性树同时进入DOM。

“验证配置”在服务端构造完整冻结快照。未通过验证时不能打开选号模拟；通过后使用该次已验证的副本。编辑任一配置节点会立即撤销旧副本及模拟结果；更改选号或开奖结果会清除旧计算结果。异步响应检查页面/品牌和输入代次，不能将早先结果装入新草稿。导出、导入会完整保留规则、属性和价格，支持后续继续编辑。

可直接导入的最小独立示例：[`lucky_group_preview.json`](../backend/internal/rules/config/examples/lucky_group_preview.json)。它就是上述第3个正码幸运组，A/B价格分别为2.5和3.5，不依赖六合彩静态选项枚举。载入完整六合彩演示模板时，前端明确生成合成属性及完整每盘669项、每项为2的演示价格；这些不是当前年度映射或真实赔率，也不会在导入缺价配置时自动补入。

## 15 C阶段保存、发布与真实资金链路

### 15.1 资源归属和使用流程

本阶段将schema-v2接入共享彩种的完整运行链路。平台管理规则目录、属性绑定和每盘每个价格键的上限；品牌只对自己接入的彩种配置销售价格、启用状态及投注限额。品牌自有schema-v1规则保留原有资源和工作流，不通过共享彩种接口修改。新配置式订单始终执行 `ConfiguredEngine`，不存在报错后改用旧解释器的路径。

实际入口在共享彩种的“玩法”详情中，使用绑定该彩种和号码模型的规则试验区。顶部未绑定彩种的通用试验区仍可离线编辑及试算；持久化和发布必须进入具体彩种。载入内置六合彩模板时使用选中彩种的明确模型；导入文件则须与该彩种模型一致，否则保存失败。

平台操作顺序：

1. 导入或配置目录、实际属性及平台上限价格；通过现有预览检查选号和计算结果。
2. 填写独立验证用例的投注、派奖和退本预期，保存草稿。模拟后可填写独立预期并加入当前请求/开奖，也可编辑用例JSON；系统不把实际计算值自动当成独立预期。
3. 选择保存版本，执行“验证已保存草稿”。至少一个用例必须通过，最多32个；校验同一快照的实际金额与独立预期，并保存hash、通过结果和完整计算明细。
4. 提交审核，审核通过或驳回；通过后发布。授权人员可以按现有允许自审的口径审核，所有动作保留操作人、修订号及审计。共享规则流程复用 `platform_game.write.platform`，没有把品牌写权限提升到平台。
5. 对首次切换的存量六合彩/加拿大彩，首次发布会在同一事务中把每个品牌现有价格、启用状态和投注限额复制到 `configured_sales`，并绑定该发布版本；所有品牌价格都须通过发布规则的上限校验，否则整次发布回滚。存量品牌不需要重填销售配置。其他新彩种或没有存量销售的品牌仍在品牌端建立销售草稿、填写价格和限额并启用。后续规则重新发布后，已有配置式销售的旧绑定会明确失效，品牌须绑定新发布版本后才能继续接新投注。

新增规则内容在保存时须能构成完整、结构有效的计算快照；保存阶段不要求已有通过的用例报告。保存任何修改都会将状态退回草稿并清除旧验证。状态流转为：

```text
draft → validated → submitted → approved → published → retired
                        └──→ rejected → draft
```

草稿/已验证/驳回状态允许修订；提交后的规则内容和用例不可修改。任何动作都检查当前修订号。发布在同一个规范彩种锁内原子替换当前版本，并停用原发布版本；不删除历史版本，不重写既有订单。

### 15.2 投注、快照和结算

用户端彩种目录由配置式游戏接口读取已经发布且品牌已接入的彩种，以 `configured` 执行协议进入动态选号。玩法ID、名称、选项及来源编码仍不决定执行分支。用户选号后先取得服务端报价，核对每注身份、积分、潜在奖级价格/各关价格及总积分，再按资金模式确认扣款或风险冻结（见第15.13节）。客户只提交规则版本、销售版本、快照hash和选号请求，不提交可信赔率或自定义结算定义。

报价及确认均复核会员身份、品牌状态、共享彩种/品牌接入可用性、自动开奖封盘条件、当前发布版本、销售版本、完整价格、逐线积分和每期/会员每期额度。规范彩种、销售和期次采用一致锁顺序；销售记录锁串行化同品牌额度检查，账户锁保护余额。当前额度汇总只读取配置式订单；有旧专用订单的期次禁止混入新配置式销售，见第15.13节。

确认调用现有 `checkedBetWrite`、`mutation.ExecuteChecked`、身份复核、合规检查、`points.Store.LockedSnapshot`、积分来源分配和 `points.Store.Post`。扣款、完整快照、报价、销售限制、来源分配、订单和审计处于同一事务，入账后再检查封盘时间；失败全部回滚。数据库也验证扣款凭据、来源总额、报价总额及购买时窗口。

配置式订单冻结规则目录、语义版本、实际属性、品牌价格、各奖级/各关报价和购买选择；后续修改平台规则、映射、平台上限或品牌价格均不改变旧单。订单表拒绝修改这些购买字段和删除记录。用户及品牌后台票据从各订单自己的快照取得双语名称和价格；品牌列表显示已授权会员账号，不用内部会员ID替代名称。

结算worker通过规范共享开奖结果发现 `placed` 订单，按订单行锁和 `SKIP LOCKED` 并发处理。它只恢复订单的冻结计算器并结算冻结报价，不查询当前规则、当前销售价格或旧六合彩计算函数。派奖使用引擎的权威汇总金额，复用既有winning来源入账；退本按冻结报价线顺序消耗原扣款分配，准确回到各原来源。派彩/退本、订单终态和审计在一个事务中提交；重复worker及账本操作键防止重复入账。

人工及现有自动开奖发布都会校验待结订单快照的开奖约束，例如已购规则声明正码与特别号互斥时，冲突的开奖不能先发布再留给结算失败。普通配置式期次不需要旧六合彩计算路径的年度属性行；既有香港来源适配器仍保留其明确要求的年度来源验证记录，配置式判奖读取的是订单冻结的通用绑定。

已发布schema-v2的彩种会从旧六合彩/加拿大销售目录中排除，旧报价、投注和规则/销售写入入口明确拒绝。新订单使用配置式报价、销售和结算；旧协议订单保留原订单快照，并继续按其原始协议结算。切换不会迁移或重判历史注单，也不会把配置式订单失败后回退到旧实现。

用户端的未确认提交在发送前按会员及彩种保存原请求、幂等键、确认报价和展示快照至sessionStorage。未知结果及刷新页面仍只重试这一份请求；会话变化由服务端签名身份上下文和当前认证再次校验。已确认成功后才清除请求，并通过原钱包读接口刷新页头余额；钱包或历史读取失败不会把已确认的扣款回执改写成“提交结果未知”。
